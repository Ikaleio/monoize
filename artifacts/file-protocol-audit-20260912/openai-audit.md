OpenAI file and media protocol audit — 2026-09-12

This read-only audit covers the working tree based on commit `6914e8ed0cf418f91c71cf993393a7934ab364a3`. It compares stable Chat Completions and Responses shapes with current official documentation and generated OpenAI SDK schemas. No implementation, specification, or permanent test changed during this audit. Fourteen offline probes ran through the shared compiled harness. Payloads use small sentinel bytes; they test conversion, not document parsing or provider acceptance.

Evidence: [fixtures](/Users/ikaleio/Projects/monoize/artifacts/file-protocol-audit-20260912/openai-fixtures.jsonl), [probe output](/Users/ikaleio/Projects/monoize/artifacts/file-protocol-audit-20260912/openai-probe.jsonl). The harness invokes native decoders and all four request encoders. `strip:true` applies provider-item filtering and nested-extra stripping. It does not reproduce routing, model capability checks, fetching, or upstream execution.

**Verified native contracts**

| Surface | Stable contract and relevant limitation |
| --- | --- |
| Responses file input | `input_file` supports `file_data`, `file_id`, `file_url`, `filename`, and optional PDF `detail`. The current guide accepts PDF, office documents, text/code, presentations, and spreadsheets. PDFs include text and page images; other documents contribute text without embedded images/charts. Spreadsheet processing uses at most the first 1,000 rows per sheet plus summaries. Each file and the combined file payload must fit the documented 50 MB limits. Chat files do not support PDF `detail`. [File inputs](https://developers.openai.com/api/docs/guides/file-inputs), [stable file schema](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/responses/response_input_file_param.py) |
| Chat file input | User content contains `{type:"file",file:{file_id}}` or `{type:"file",file:{filename,file_data}}`. There is no `file_url` member. The generic schema does not establish equal model support for every document subtype; the guide supplies Chat PDF examples. [Chat content schema](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/chat/chat_completion_content_part_param.py) |
| Base64 files | Official examples use `data:<MIME>;base64,<bytes>` for `file_data`; the schema itself only specifies a string. The current codec correctly splits this form and rebuilds the MIME prefix. Raw-base64 compatibility input has no explicit MIME and currently defaults to `application/octet-stream`. [File examples](https://developers.openai.com/api/docs/guides/file-inputs) |
| Images | Responses uses `input_image.image_url` for external URLs or data URLs, and also accepts `file_id`. Chat uses nested `image_url.url`; its image schema has no file-id member. Documented image formats are PNG, JPEG, WEBP, and non-animated GIF. The current vision guide states 512 MB total request payload and 1,500 images. These are provider limits, not verified gateway limits. [Vision guide](https://developers.openai.com/api/docs/guides/images-vision), [Responses image schema](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/responses/response_input_image_param.py), [Chat image schema](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/chat/chat_completion_content_part_image_param.py) |
| Tool results | Responses function output accepts a string or an array of `input_text`, `input_image`, and `input_file` content. Chat tool-message content accepts only text. [Responses result union](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/responses/response_function_call_output_item_list_param.py), [Chat tool-message schema](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/chat/chat_completion_tool_message_param.py) |

The `input_audio` probe is an unimplemented/unsupported surface boundary, not a confirmed valid-stable-input defect. Chat input audio has its own input-audio member. [Stable Responses union](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/responses/response_input_content_param.py), [Chat content union](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/chat/chat_completion_content_part_param.py) |

**Findings**

1. **Responses assistant media becomes invalid `output_image` / `output_file` content. Executed; implementation/spec mismatch.**

   Minimal inputs are `openai-assistant-image` and `openai-assistant-file`. Both use an assistant input message with an input-media block. Encoding changes these to `message.content[].type="output_image"` or `"output_file"`. Neither discriminator belongs to the stable ResponseOutputMessage content union, which contains output text and refusal. The role-dependent dispatch is [message_items.inc.rs:140](/Users/ikaleio/Projects/monoize/src/urp/encode/openai_responses/message_items.inc.rs:140); request encoding calls it from [tool_call.inc.rs:341](/Users/ikaleio/Projects/monoize/src/urp/encode/openai_responses/tool_call.inc.rs:341). [Official output-message schema](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/responses/response_output_message_param.py).

   PR4d correctly rejects invented output-media blocks, but it also says assistant history must use only output-message blocks. That stronger restriction conflicts with the current stable SDK: `EasyInputMessageParam` admits assistant role and an input-content list containing text, images, and files. An easy-input assistant media representation is therefore a schema-supported candidate. No live request tested its model-specific acceptance. [Easy-input schema](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/responses/easy_input_message_param.py), [input-content list](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/responses/response_input_message_content_list_param.py).

   The same generated output-media shape also occurs in non-stream responses and synthetic streams. The live encoder has independent output-media writers at [encode_loop_part1.inc.rs:3415](/Users/ikaleio/Projects/monoize/src/urp/stream_encode/openai_responses/encode_loop_part1.inc.rs:3415). These may serve permissive clients, but they are not proof of stable OpenAI schema compatibility.

2. **Responses live multimodal tool results use output discriminators. Static trace; implementation bug against PR7/TR-4.**

   A ToolResult containing an image and file uses `encode_tool_result_output` during live node completion. That helper calls `encode_image_part` and `encode_file_part`, which write `output_image` and `output_file`. See [encode_loop_part1.inc.rs:2312](/Users/ikaleio/Projects/monoize/src/urp/stream_encode/openai_responses/encode_loop_part1.inc.rs:2312), [the helper:3528](/Users/ikaleio/Projects/monoize/src/urp/stream_encode/openai_responses/encode_loop_part1.inc.rs:3528), and finding 1's media writers. The stable function-output union requires input-media types. [Official result union](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/responses/response_function_call_output_item_list_param.py).

   In contrast, the executed `openai-tool-multimedia` request probe preserves all three parts with correct input discriminators. Its non-stream helper is [request_response.inc.rs:1](/Users/ikaleio/Projects/monoize/src/urp/encode/openai_responses/request_response.inc.rs:1). Synthetic Responses streams start from non-stream `encode_response` at [synthetic.inc.rs:9](/Users/ikaleio/Projects/monoize/src/urp/stream_encode/openai_responses/synthetic.inc.rs:9). A terminal-only roundtrip can therefore pass while the earlier live item event has the wrong shape. Recommended stream probe: provide ToolResult NodeStart/NodeDone plus ResponseDone, then inspect each `response.output_item.done.item.output[]` separately from the terminal response. This exact live fixture was not executed in this audit.

3. **Same-Responses filename metadata disappears for URL and file-id sources. Executed; canonical representation gap.**

   `openai-file-filename-url` and `openai-file-filename-id` each supply `filename:"renamed.pdf"`. The decoded File has no filename, and same-Responses re-encoding omits it. The parser returns URL/FileId variants before retaining filename, then removes `filename` from extras: [decode/mod.rs:557](/Users/ikaleio/Projects/monoize/src/urp/decode/mod.rs:557), [decode/mod.rs:683](/Users/ikaleio/Projects/monoize/src/urp/decode/mod.rs:683). Only FileSource::Base64 owns a filename under URPV2-13/TRC4. The corresponding encoders can only write URL or id: [request_response.inc.rs:222](/Users/ikaleio/Projects/monoize/src/urp/encode/openai_responses/request_response.inc.rs:222).

   The official stable object defines filename alongside all three source options. No mutual-exclusion restriction appears in that generated schema. Thus this is confirmed schema-member loss, although the provider's interpretation of a filename accompanying an existing file id was not exercised. A shared optional filename owner or documented source-specific rejection is needed before claiming preservation. [Official file-input schema](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/responses/response_input_file_param.py).

4. **Chat media encoding does not enforce the message role. Executed requests; response/stream paths traced statically.**

   `openai-assistant-image` and `openai-assistant-file` become assistant Chat content arrays containing `image_url` and `file`. `openai-chat-system-file` preserves a file under system role. The generic content writer accepts media without a role check at [openai_chat.rs:86](/Users/ikaleio/Projects/monoize/src/urp/encode/openai_chat.rs:86), called from the ordinary-message loop at [openai_chat.rs:1020](/Users/ikaleio/Projects/monoize/src/urp/encode/openai_chat.rs:1020).

   Stable assistant history content admits text/refusal, with previous audio referenced through `audio.id`. System/developer content is text-only. These probes are outside those role schemas. PC2's broad content-preservation contract needs a target-role qualification. [Assistant schema](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/chat/chat_completion_assistant_message_param.py), [system schema](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/chat/chat_completion_system_message_param.py), [developer schema](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/chat/chat_completion_developer_message_param.py).

   Non-stream response encoding similarly creates assistant media arrays at [openai_chat.rs:747](/Users/ikaleio/Projects/monoize/src/urp/encode/openai_chat.rs:747). Both live and synthetic streams call that encoder through [stream_encode/openai_chat.rs:1480](/Users/ikaleio/Projects/monoize/src/urp/stream_encode/openai_chat.rs:1480). Stable Chat response `message.content` is optional text, not a media array. Preserve this as an explicitly named compatibility extension if required; do not report it as native Chat output support. [Official response-message schema](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/chat/chat_completion_message.py).

5. **PDF detail is retained for same-Responses; raw codec calls can leak it to Chat. Executed; runtime distinction matters.**

   `openai-file-filename-id` without stripping emits outer Chat file-block `detail:"high"`. The parser leaves detail in File extras and Chat merges those extras at [openai_chat.rs:162](/Users/ikaleio/Projects/monoize/src/urp/encode/openai_chat.rs:162). This is outside the Chat file object. The paired `openai-file-detail-stripped` probe omits detail in Chat while preserving the typed OpenAI file id. Consequently, the normal cross-family stripping step prevents this observed leak. It is a raw-adapter eligibility limitation, not a demonstrated routed-request defect. Same-Responses encoding without stripping keeps detail as intended. The probe harness strips even when asked to encode back to the source family; its stripped same-Responses result must not be mistaken for actual same-family routing behavior. [Responses detail schema](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/responses/response_input_file_param.py), [Chat file schema](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/chat/chat_completion_content_part_param.py).
