## Diagnose with logs first

Open **Request Logs** in the dashboard before you change configuration. Each failed request row shows the error code, the HTTP status, and every failed upstream attempt. Enable [request capture](/en/docs/request-logs) to inspect the exact upstream payloads.

## Authentication errors

### `401 unauthorized`

1. Confirm the key starts with `sk-` and is complete.
2. Confirm the key is enabled and not expired in **API Keys**.
3. Confirm the owning user account is enabled.
4. Confirm the header format: `Authorization: Bearer sk-...` or `x-api-key: sk-...`.

### `403 model_not_allowed`

The key has model limits enabled and the requested model equals no entry. Add the exact logical model name to the key's model list, or disable model limits.

### `403 ip_not_allowed`

The client IP is not in the key's IP whitelist. Add the address or CIDR range, or clear the whitelist. When Monoize runs behind a reverse proxy, confirm the proxy forwards the real client IP.

## Routing errors

### `502 upstream_error`

No route serves the model, the final attempt failed without an upstream code, or the upstream rejected the Channel credential. Check in this order:

1. **Channel credential rejected.** The body has `upstream_status` set to `401`, `403`, or `407`. Fix the Channel key or its permissions. The client key is valid.
2. **Transport failure.** The message is `failed to request upstream`. Check the Channel base URL and proxy.
3. **No route exists.** Confirm at least one enabled Provider has an enabled Channel with weight above zero that maps the model.
4. **Groups do not intersect.** The key's groups must share at least one group with the Provider. See [API Keys](/en/docs/dashboard/api-keys).
5. **All Channels unhealthy.** The circuit breaker skips unhealthy Channels during cooldown. Read the failed attempts on the log row to find the root upstream error.
6. **Multiplier cap.** A key with `max_multiplier` skips model entries priced above the cap.

### Other upstream statuses and codes

The client receives the final upstream status and code, for example `429 rate_limit_exceeded`. This also applies with `stream: true`. Read the failed attempts on the log row to see each hop. An attempt that received `2xx` before failing can make a later error arrive in the stream with HTTP `200`.

### `400 unsupported_tool`

The request sends an `openrouter:*` tool or another tool type without a Chat encoding to a Chat dialect that cannot represent it. Remove the tool, or route the model to a Channel with the `openrouter` or `generic` dialect. See [API Endpoints](/en/docs/endpoints).

### A built-in tool has no effect

Cross-family routes keep only mapped built-in tools. Monoize drops other built-in tools without an error, and a forced choice of a dropped tool becomes `auto`. See [API Endpoints](/en/docs/endpoints).

### An error message shows `***`

Monoize masks hostnames, URLs, IP addresses, and API keys in client error text. Admins read the full text in [Request Logs](/en/docs/request-logs).

### Requests always hit one Channel

Weighted selection is random per request. Small samples can look unbalanced. Check also whether session affinity binds the conversation to one Channel on purpose.

## Billing errors

### `402 insufficient_balance`

The user balance, or the key's sub-account balance, is zero or negative. Top up the balance in **Users**, or disable the sub-account option on the key.

### Charges look wrong

Charge = base price × group `billing_ratio` × Channel model `multiplier`. Confirm the model has an enabled price row on the **Model Pricing** page. Check the group's billing multiplier on the **Groups** page. Check the multiplier on the Channel model entry. A multiplier of `0` makes the Channel free.

## Streaming problems

### The stream stops mid-response

Monoize never switches upstreams after the first protocol event. A stream that dies mid-response reflects an upstream failure. The client receives an in-stream `error` event, because the HTTP status is already `200`. Read the log row and enable capture to see the raw upstream frames.

### A client waits for `[DONE]`

Only Chat Completions streams send `data: [DONE]`. Responses and Messages streams end after their terminal event. Update the client to stop at the terminal event.

### A Chat stream has no usage chunk

Set `stream_options.include_usage` to `true` in the request. Billing does not depend on this option.

### A Responses WebSocket closes or rejects events

- `websocket_connection_limit_reached` means that the connection reached a turn, byte, or age limit. Open a new connection. The default age limit is 60 minutes.
- `previous_response_not_found` means that the connection has no such cached response. Resend the complete history.
- `response.steer.failed` with `steering_not_supported` means that the turn or Channel cannot steer. Wait for the response to finish, then send the input in a new turn.

See [Responses WebSocket](/en/docs/endpoints) for all codes.

### A client rejects long SSE frames

Some clients limit SSE frame length. Add the `stream_split_sse_frames` transform to the serving Provider. See [Stream: split oversized SSE frames](/en/docs/transforms/stream_split_sse_frames).

### The upstream requires streaming

Add the `stream_force` transform to force `stream: true` toward the upstream. Monoize still returns a non-streaming response to the client when the client asked for one.

## Protocol conversion questions

### Reasoning disappears after conversion

Some upstreams return reasoning in nonstandard fields. Use the reasoning transforms to restore or reshape it. Start with [Transforms](/en/docs/transforms).

### Provider-specific fields are missing upstream

Cross-family conversion removes provider-specific nested fields with no safe target representation. Use the `field_set` transform to reinstate a field for one Provider.

### Provider-specific fields are missing from a response

Cross-family responses lose provider-specific fields, such as `metadata`, `container`, and `stop_details`. This rule has no setting. Route the model to a Channel of the same protocol family to keep these fields.

### A client rejects tool-call numbers such as `4338.0`

Some upstreams emit whole numbers as JSON floats in tool-call arguments. Codex `write_stdin` parses `session_id` as an integer and rejects `4338.0`. Monoize rewrites integer-valued floats in tool-call arguments to JSON integers before the client receives them. You do not need a transform rule for this rewrite.

## Dashboard access

### Lost admin password

Another `super_admin` can reset it in **Users**. When no `super_admin` remains, reset it directly in the database.

### First account is not admin

The first registered account becomes `super_admin`. This rule applies once. Later accounts default to `user`.
