## 路由選擇

存在有效訂閱時，Monoize 在選擇 Provider 前，將金鑰群組與訂閱群組取交集，並保留金鑰群組順序。
請求不能使用交集之外的 Provider。

對每個請求，Monoize 按以下順序解析路由：

1. **模型重新導向。** 先執行 API 金鑰規則，再執行全域規則。第一條匹配的規則重寫模型名。
2. **Provider 選擇。** Monoize 收集滿足以下條件的已啟用 Provider：至少有一個已啟用、權重大於零的 Channel 服務該模型，且群組與金鑰群組有交集。群組順序決定優先順序；同一群組內按 Provider 優先級排序。
3. **Channel 選擇。** 在選中的 Provider 內，Monoize 按權重隨機排序候選 Channel。Channel $i$ 被首先嘗試的機率為：

```math
P(i) = \frac{w_i}{\sum_{j=1}^{n} w_j}
```

因此權重為 `2` 的 Channel 獲得的流量是權重為 `1` 的 Channel 的兩倍。

## 重試與備援

Monoize 按巢狀順序嘗試路由：先在一個 Provider 內遍歷 Channel，再前進到下一個 Provider。

- 每個 Channel 獲得 `channel_max_retries + 1` 次嘗試。預設為 1 次嘗試，不做 Channel 內重試。
- `channel_retry_interval_ms` 在 Channel 內重試之間插入等待。預設為 `0`。
- `max_retries` 限制整個 Provider 的總嘗試次數。
- 一個 Provider 耗盡後，Monoize 繼續嘗試下一個符合條件的 Provider。
- 所有 Provider 都耗盡後，用戶端收到最後一次失敗嘗試的狀態碼和錯誤。參見[錯誤回應](/zh-TW/docs/endpoints)。
- 最後一次上游傳回 `401`、`403` 或 `407` 時，用戶端收到 `502`，錯誤碼為 `upstream_error`。沒有任何嘗試的請求同樣傳回 `502 upstream_error`。

### 哪些錯誤會重試同一 Channel

| 錯誤 | 同 Channel 重試 | 前進到下一路由 |
| --- | --- | --- |
| 內建分類和最終分類都不是持續性故障的 HTTP `408`、`429`、`5xx` | 是 | 是，Channel 預算耗盡後 |
| 逾時、連線被拒絕或重設 | 是 | 是，Channel 預算耗盡後 |
| 內建分類或最終分類為持續性上游故障 | 否 | 是，立即前進 |
| 其他上游錯誤（如 `400`、`401`、`404`） | 否 | 是，立即前進 |
| 上游協定無法表示請求中的媒體內容 | 否 | 是，立即前進 |
| Monoize 的其他錯誤（如認證、餘額、請求驗證、請求編碼或計費錯誤） | 否 | 否；路由終止 |

## 串流保證

Monoize 在第一個上游嘗試被接受後傳送 SSE 回應標頭。HTTP 嘗試在收到 `2xx` 狀態碼時被接受。上游 WebSocket 嘗試在收到第一個非 Provider 控制事件時被接受。此前的失敗傳回原生 JSON 錯誤，而不是 SSE。

傳送回應標頭後，備援繼續有效，直到第一個協定資料或錯誤事件。Monoize 緩衝回應開始事件和 Provider 控制事件（例如 `codex.rate_limits`），直到第一個輸出事件。緩衝區最多容納 256 個事件。SSE 心跳在回應標頭之後開始，不會結束備援。

如果回應標頭傳送後所有路由都失敗，錯誤會在串流中傳回，因為 HTTP 狀態碼已經是 `200`。第一個協定事件之後，Monoize 絕不切換。因此可見的串流始終來自同一次生成。

## 斷路器

每個 Provider 都有 `circuit_breaker_enabled` 開關。設為 `false` 後，Monoize 不再依據或追蹤該 Provider 的健康狀態，也不再進行主動探測。主動探測沒有獨立開關。

儀表板顯示三種 Channel 健康狀態：

- **健康。** Channel 符合其他路由條件時，可以接收流量。
- **不健康。** 在 Channel 恢復前，Monoize 不會向它轉送任何請求。
- **已停用。** `enabled` 為 `false`。無論是否啟用斷路器，Channel 都不會接收流量。

啟用斷路器後，持續性故障會立即使 Channel 變為不健康。暫時性故障和流量限制錯誤在 30 秒內累計達 3 次時，預設會觸發斷路。啟用 `per_model_circuit_break` 後，Monoize 會分別追蹤 Channel 中各模型的健康狀態。某個模型不健康時，不影響同一 Channel 中其他模型接收流量。

### 故障分類

Monoize 先依清單順序檢查 `monoize_failure_classification_rules`，再套用內建分類。第一條相符的規則決定最終類別。規則適用於轉送、主動探測和 Channel 測試中的上游錯誤，包括 HTTP 錯誤，以及上游在成功回應的本文或串流中回報的錯誤。Monoize 本身的錯誤和傳輸失敗不參與比對。

規則要求兩個欄位都相符：

- `status_codes`：清單必須包含上游實際傳回的 HTTP 狀態碼。HTTP `200` 串流中的錯誤以 `200` 比對。空清單符合任意狀態碼，也包括沒有 HTTP 狀態碼的上游錯誤。
- `keyword`：去除前後空白的關鍵字必須出現在上游錯誤的 `message`、`code` 或 `type` 中。Monoize 分別比對各欄位，不區分大小寫。比對使用 Unicode 簡單小寫對應，不依地區設定轉換，也不做正規化。

從未儲存此設定時，Monoize 會依序使用以下規則：

| `status_codes` | `keyword` | `class` |
| --- | --- | --- |
| `[503]` | `no available account` | `persistent` |
| `[]` | `no credits remaining` | `persistent` |
| `[503]` | `no available gemini accounts` | `persistent` |
| `[503]` | `no available openai accounts` | `persistent` |
| `[503]` | `no available grok accounts` | `persistent` |
| `[503]` | `no available compatible accounts` | `persistent` |
| `[502]` | `upstream authentication failed` | `persistent` |
| `[502]` | `upstream access forbidden` | `persistent` |
| `[429]` | `额度已用完` | `persistent` |

這些預設規則涵蓋 sub2api 等中繼服務的金鑰層級錯誤。沒有這些規則時，這些錯誤會被歸為暫時性或限流故障。`429` 視窗限額（例如 `api key 5小时限额已用完`）不符，仍以限流處理。

儲存的清單會取代所有預設規則。儲存空清單可只使用內建分類。在[系統設定](/zh-TW/docs/dashboard)中編輯清單。

如果沒有規則相符，Monoize 會依下列順序套用第一條相符的內建規則。比對上游錯誤的 `code` 和 `type` 時，先去除前後空白，再忽略 ASCII 字母的大小寫。

1. `persistent`：上游額度用盡，即使傳回 HTTP `429`。錯誤識別碼包括 `insufficient_quota`、`credit_balance_exhausted`、`credit_balance_too_low`、`insufficient_balance` 和 `billing_hard_limit_reached`。
2. `rate_limited`：其他 HTTP `429`，包括帶有 `quota_exceeded` 的 `429`。
3. `persistent`：HTTP `401`、`402`、`403`、`404`、`405`、`407`、`410`、`415` 或 `451`。
4. `rate_limited`：`rate_limit_error`、`rate_limit_exceeded` 或 `too_many_requests`。
5. `persistent`：`account_deactivated`、`account_suspended`、`authentication_error`、`deployment_not_found`、`invalid_api_key`、`model_not_found`、`model_not_supported`、`no_available_account`、`permission_denied`、`quota_exceeded` 或 `unsupported_model`。
6. `transient`：HTTP `408`、HTTP `5xx`，或 `overloaded_error`、`server_error`、`service_unavailable`、`temporarily_unavailable`。逾時和連線失敗也屬於暫時性故障。

啟用斷路器後，轉送失敗的最終類別決定斷路行為：

| 最終類別 | 被動斷路 | 重試同一個 Channel | 其他 Channel 的失敗取樣 |
| --- | --- | --- | --- |
| `persistent` | 立即斷路 | 不重試 | 不取樣 |
| `rate_limited` | 累計至門檻；觸發斷路後，由遵守流量限制的設定決定等候時間 | 只在內建重試規則允許時 | 不取樣 |
| `transient` | 累計至門檻 | 只在內建重試規則允許時 | 可能為同一 Provider 中符合條件的同源 Channel 記錄一次失敗 |

只有可重試的暫時性 HTTP `502`、`503` 或 `524` 錯誤回應才會影響其他 Channel，串流中的錯誤不會。基底網址的協定、主機和連接埠相同即為同源。規則可以讓 HTTP `400` 納入健康判定，但不能讓它變得可重試。規則不能增加內建規則不允許的重試。

### 主節點上的探測復原

主節點透過主動探測讓非 Replicate Channel 恢復健康。通常，Monoize 會在斷路後等候一個探測間隔，再進行第一次探測。探測失敗會將連續成功次數歸零，再等一個間隔才進行下一次探測。下文的流量限制規則可取代這兩種等候時間。

連續成功次數達到門檻後，Channel 或模型才會恢復健康。探測成功但未達門檻時，Monoize 會在一個間隔後安排下次探測。探測間隔結束只表示可以探測，不會恢復轉送流量。Monoize 不會探測已停用的 Provider、已停用的 Channel 或權重為零的 Channel。

| 探測設定 | 全域設定鍵 | Provider 或 Channel 覆寫欄位 | 預設值 |
| --- | --- | --- | --- |
| 探測間隔 | `monoize_active_probe_interval_seconds` | `active_probe_interval_seconds_override` | 30 秒 |
| 成功門檻 | `monoize_active_probe_success_threshold` | `active_probe_success_threshold_override` | 成功 1 次 |
| 探測模型 | `monoize_active_probe_model` | `active_probe_model_override` | `null` |
| 串流探測 | `monoize_active_probe_stream` | `active_probe_stream_override` | 開啟（`true`） |

每項設定都依 Channel 覆寫值、Provider 覆寫值、全域值的順序採用第一個非 `null` 的值。將串流探測的覆寫值設為 `false` 會關閉串流，不會繼承下一層設定。

以 Channel 為單位斷路時，如果該 Channel 提供設定中的探測模型，就使用該模型。如果沒有設定，或該 Channel 未提供設定中的模型，則選擇依字典順序排列的第一個邏輯模型鍵。啟用 `per_model_circuit_break` 後，Monoize 會用各不健康模型自己的邏輯模型鍵進行探測。

Responses、Chat Completions、Messages 和 Gemini 的探測請求一開始只包含一則 `hi` 訊息，輸出上限為 16 個 token，預設要求串流回應。Monoize 先套用 Provider 的請求變換，再套用全域請求變換。變換可以修改輸出上限或串流選項。Monoize 使用與一般轉送相同的編碼器，一律透過 HTTP 傳送探測請求。變換或編碼出錯時，探測失敗，不會向上游送出請求。

探測成功須取得 HTTP `2xx` 回應。串流探測還要求轉送所用的解碼器讀到終止事件，且沒有送出錯誤事件。非串流探測則要求該解碼器成功讀取回應本文。圖片與決策類 Channel 使用原生非串流探測，不套用變換，也不採用串流探測設定。

### 定時復原

任何節點上的 Replicate Channel，以及複本節點上的所有 Channel，都採用定時復原，不進行主動探測。一般等候時間（`cooldown_seconds`）預設為 60 秒。透過全域設定 `monoize_passive_cooldown_seconds` 或 Channel 的 `passive_cooldown_seconds_override` 調整。等候結束後，Channel 或模型無須探測即可恢復健康。

### 遵守上游流量限制

`monoize_honor_rate_limit` 預設為 `false`。可透過 Provider 或 Channel 的 `honor_rate_limit_override` 覆寫全域設定。Monoize 依 Channel、Provider、全域的順序，採用第一個非 `null` 的值。明確設為 `false` 表示關閉，而不是繼承。

啟用後，如果觸發斷路的故障最終歸類為 `rate_limited`，首次探測或定時復原前會改用流量限制冷卻時間。這段時間預設為 15 秒。透過全域設定 `monoize_passive_rate_limit_cooldown_seconds` 或 Channel 的 `passive_rate_limit_cooldown_seconds_override` 調整。

如果上游傳回有效且較長的 `Retry-After`，Monoize 會採用該值。比較前，Monoize 會將從回應標頭解析出的時間限制在 3600 秒以內。有效的 `retry-after-ms` 優先於 `Retry-After`，並無條件進位至整秒。探測本身若受流量限制，則根據該次探測的回應套用相同規則。關閉此設定時，流量限制錯誤仍使用一般探測間隔或定時復原等候時間。

### 儀表板測試和啟用開關

執行 [Channel 測試](/zh-TW/docs/dashboard/providers-and-channels)，無須等候主動探測即可確認是否恢復。測試與主動探測採用相同的請求處理流程和成功判定規則。對補全類測試，**快速測試**採用 Channel 實際生效的串流設定；在測試對話框中可以選擇初始串流模式。這項測試不支援 Replicate 補全請求。

測試通過後，受測的 Channel 或模型會恢復健康。啟用斷路器時，如果測試遇到持續性上游故障，受測對象就會變為不健康。如果已經不健康，原本的復原排程不變。其他測試失敗不會改變健康狀態。啟用 `per_model_circuit_break` 時，測試只影響受測模型。

啟用或停用 Channel 都會清除其健康記錄，包括各模型的健康狀態。

## 工作階段親和

Monoize 可以優先選擇先前服務該工作階段的 Channel。可在全域或 Channel 層設定親和。優先 Channel 仍須符合資格與健康規則。Responses 的 `previous_response_id` 歷史由 Monoize 在內部解析，不要求上游保存狀態。

## 時間指標

[請求日誌](/zh-TW/docs/request-logs)中的每一行記錄總耗時、首位元組時間和可見輸出的每秒 Token 數。修改權重之前，用這些數值比較各個 Channel。
