## 基础 URL 与认证

将请求发送到 Monoize 的监听地址。默认为 `http://localhost:8080`。使用以下任一请求头携带 API 密钥：

```bash
Authorization: Bearer sk-...
# 或
x-api-key: sk-...
```

下列每个端点都有 `/api` 前缀别名，例如 `/api/v1/chat/completions`。当客户端硬编码了 `/api` 路径时使用别名。

任何端点都可以到达任何上游类型。例如，客户端调用 `/v1/messages`，而路由通过 `chat_completion` 类型的 Channel 服务该模型。Monoize 在两个方向上转换协议。决策 Channel 例外，参见下文“决策”一节。

Chat 路由会保留 OpenRouter 的 `configuration_update` 消息，包括空内容更新。文件 data URI 转为 Messages 文档时会保留 MIME 类型。Messages 流会保留 `citations_delta` 引用。Responses 内容过滤终止会保留为未完成状态，不会误报为长度限制。

Chat 与 Responses 会将支持的 URL 引用转换为目标格式。无法表示的引用位置仅在原协议中保留。Token logprobs 与对应文本关联；文本修改后，不再匹配的概率会被丢弃。Responses 失败终态保留部分输出、用量和错误详情。Chat 与 Messages 将失败或取消状态输出为错误。Messages 保留暂停、压缩和上下文限制的停止原因。计费包含上游报告的所有压缩迭代，不会重复计算主生成用量。

协议转换分别保留 raw 推理、可读摘要和不透明的回传载荷。删除 raw 推理后，不会用摘要恢复它。Messages 的 thinking 文本映射为摘要，signature 保持不透明。非法流生命周期和格式错误的已知事件会返回错误。完整 Messages 请求和响应拒绝截断的工具 JSON；原生 max_tokens 流可保留未完成的参数字节。

Chat 中具有相同稳定身份的推理分片会累计到同一节点。最终快照只补充尚未发送的文本后缀，独立的 detail 保持分离。

工具参数可以实时输出。工具签名信封等待工具终态确定后再输出，签名始终作为完整的不透明值处理。

Messages 请求会一起转换带对象 `input_schema` 的 custom 工具、JSON 对象调用参数和关联结果，并保留 `call_id`。无效的 schema 或参数会返回错误。

Responses 对象包含非 null 的 error 且缺少有效 status 时会返回错误。空对象会被拒绝。没有错误且包含 output 数组的兼容响应仍可省略 status。

跨协议族响应指上游类型与端点协议不同的响应。`gemini` 上游始终属于跨协议族。无论是否流式，Monoize 都会从这类响应中移除提供商私有字段，例如 `metadata`、`status`、`phase`、`prompt_cache_key`、`container`、`diagnostics` 和 `stop_details`。此规则没有开关。Monoize 还会把响应 id 改写为目标前缀：`resp_`、`chatcmpl-` 或 `msg_`。计费、请求日志和请求捕获读取原始值。

## 列出模型

```bash
curl http://localhost:8080/v1/models \
  -H "Authorization: Bearer sk-..."
```

响应以 OpenAI 列表格式返回调用密钥可用的逻辑模型。

## Chat Completions

```bash
curl http://localhost:8080/v1/chat/completions \
  -H "Authorization: Bearer sk-..." \
  -H "Content-Type: application/json" \
  -d '{
    "model": "my-model",
    "messages": [{ "role": "user", "content": "Hello" }],
    "stream": true
  }'
```

设置 `"stream": true` 使用服务器推送事件。省略或设为 `false` 则返回单个 JSON 响应。

Chat 流以 `data: [DONE]` 结束。只有请求将 `stream_options.include_usage` 设为 `true` 时，Monoize 才发送用量块。此选项不影响计费。

### Chat 方言

对每次 `chat_completion` 尝试，Monoize 根据 Channel base URL 的主机和上游模型选择一种方言。按表格顺序取第一条匹配项。

| 方言 | 匹配条件 | assistant 历史中的推理字段 | 生成的输出 Token 字段 |
| --- | --- | --- | --- |
| `openai` | 主机为 `api.openai.com` 或 `*.openai.azure.com` | 无 | `max_completion_tokens` |
| `openrouter` | 主机为 `openrouter.ai` 或 `*.openrouter.ai` | `reasoning_details` 和 `reasoning` | `max_tokens` |
| `vercel` | 主机为 `ai-gateway.vercel.sh` | `reasoning_details` 和 `reasoning` | `max_tokens` |
| `deepseek` | 主机为 `api.deepseek.com`，或模型 id 包含 `deepseek` | `reasoning_content` | `max_tokens` |
| `generic` | 其他所有尝试 | `reasoning_details` 和 `reasoning` | `max_completion_tokens` |

- 主机规则优先。OpenRouter 上的 DeepSeek 模型使用 `openrouter` 方言。
- 方言不能按 Channel 覆盖。重试到其他 Channel 时会重新选择方言。
- `generic` 采用 OpenRouter 兼容行为。未列出主机上的严格中转站可能拒绝其扩展字段。
- Chat 客户端保留自己使用的输出 Token 字段名，`deepseek` 除外。表格适用于其他客户端。
- 推理力度使用 `reasoning_effort`，包括 `none`。请求同时带两个字段时，`reasoning.effort` 优先于 `reasoning_effort`。
- 原生 Chat `reasoning` 对象只发送给 `openrouter`、`vercel` 和 `generic` 上游。`openai` 和 `deepseek` 上游不会收到。
- 没有推理力度时，预算或启用模式在 `openrouter` 和 `vercel` 上转为 `reasoning.max_tokens` 或 `reasoning.enabled`。其他方言省略这些值。
- Monoize 不会同时发送推理力度和 `reasoning.max_tokens`。
- `openai` 方言省略原生 `thinking` 对象。只有 `vercel` 方言接收 `providerOptions`。
- Chat 响应保留上游的推理字段形式。上游的 `reasoning_content` 仍是 `reasoning_content`，不会额外生成 `reasoning_details`。

## Responses

```bash
curl http://localhost:8080/v1/responses \
  -H "Authorization: Bearer sk-..." \
  -H "Content-Type: application/json" \
  -d '{
    "model": "my-model",
    "input": "Hello",
    "stream": true
  }'
```

说明：

- 将返回的 Monoize id 作为 `previous_response_id`，即可通过任意上游协议续接响应。历史记录按 API Key 隔离。
- HTTP 历史默认使用 `store=true`，在当前进程中最多保留 30 分钟。重启或缓存淘汰会移除记录。
- 设置 `store=false` 可关闭 HTTP 历史保留。未知或过期的 id 返回 `400 previous_response_not_found`。收到该错误后，请重新发送完整历史。
- 每次请求都应提供当前 instructions 和控制参数。前一请求的顶层 `instructions` 不会自动继承。
- `POST /v1/responses` 的流在终态 JSON 事件后结束，没有 `data: [DONE]` 帧。`sequence_number` 从 `0` 开始。
- 长时间运行的 Agent 会话可使用 WebSocket。参见 [Responses WebSocket](#responses-websocket)。
- `POST /v1/responses/compact` 压缩一段会话。
- compact 请求需要 `input` 或 `previous_response_id`。两者都没有时返回 `400 invalid_request`。
- Monoize 将原生 compact 请求体转发到上游 `POST /v1/responses/compact`。
- 选定 Channel 后，如果该 Channel 映射了 `{model}-openai-compact`，Monoize 把线路模型改成这个兄弟模型。否则发送会话模型。
- 计费使用会话模型的价格。兄弟模型 ID 不需要单独的价格记录。

`POST /v1/responses` 发往 Responses 上游时，Monoize 保留显式传入的 `include` 和 `reasoning.summary`。它不会自动添加 `reasoning.encrypted_content` 或默认摘要设置。

Chat Completions 或 Messages 客户端路由到 Responses 上游时，如果请求没有对应值，Monoize 将 `include` 设为 `["reasoning.encrypted_content"]`，将 `store` 设为 `false`。无状态客户端因此能在工具轮次之间保留推理。Messages 的 `thinking` 映射为 `reasoning.effort` 和 `reasoning.summary`。

## Responses WebSocket

将 `GET /v1/responses` 或 `GET /v1/codex/responses` 升级为 WebSocket。两个路径都有 `/api` 别名，认证方式与 `POST /v1/responses` 相同。`POST /v1/codex/responses` 与 `POST /v1/responses` 使用同一个 HTTP 处理器。

每条客户端消息是一个文本帧中的一个 JSON 对象。Monoize 将每个事件作为一个 JSON 文本帧发送，不使用 SSE 分帧，也不发送 `[DONE]`。每个轮次都有独立的请求 ID、请求日志行和计费。

### 协议版本

- `OpenAI-Beta: responses_websockets=2026-02-06` 选择 v2。客户端同时发送两个版本时，v2 优先。
- `OpenAI-Beta: responses_websockets=2026-02-04` 选择 v1。
- 没有版本请求头时，`response.append` 选择 v1。`response.create` 选择 v2，除非连接已使用 v1。
- v2 保留上游的终态事件类型。
- 对于后续 `response.append` 可以追加的已完成响应，v1 发送 `response.done`。其他终态事件保留原类型。
- `response.append` 是本地模拟。Monoize 根据连接缓存构造下一个请求，上游不会收到 `response.append`。

### 上游传输

- 路由到 Responses Channel 的轮次可以打开上游 WebSocket。`POST /v1/responses` 始终使用 HTTP。
- 握手失败时，同一次尝试改用 HTTP SSE。状态 `101` 之后的失败属于普通上游失败，不会回退到 HTTP。
- 每个 lane 将一个上游会话固定到一个 Channel 和上游模型。在该会话上续接时只发送新增输入。
- 如果上游返回 `previous_response_not_found`，或复用的会话提前失败，Monoize 会在新会话上重放完整历史。客户端看不到错误。
- 路由或模型变化会关闭固定会话。关闭客户端连接会关闭所有固定会话。
- 对发往 Responses Channel 的每个生成轮次，Monoize 都把 `reasoning.encrypted_content` 加入 `include`，除非客户端已经列出。预热轮次和其他 Channel 类型不会收到此值。
- 对这些轮次，Monoize 从客户端事件中移除 `encrypted_content`，并保留在连接缓存中。自行列出此值的客户端会收到 `encrypted_content`。
- Monoize 把 `client_metadata` 转发到上游 WebSocket 的 create 请求，并在同一 Channel 上重放 `x-codex-turn-state`。

### Lane

lane 是一条连接内的请求队列。在 `response.create` 或 `response.append` 上设置 `stream_id` 可选择命名 lane。省略时使用默认 lane。

- `stream_id` 是 1 到 256 个字符的字符串，字符取自 `[A-Za-z0-9_.-]`。
- 一条连接最多接受 32 个命名 lane。默认 lane 不计入。
- 同一 lane 内的轮次按到达顺序执行。不同 lane 并发执行。
- 一条连接最多同时生成 16 个轮次。其他轮次在各自 lane 中等待。
- 命名 lane 的每个事件都带 `stream_id`，包括错误和确认事件。默认 lane 的事件不带此字段。
- Monoize 不会把 `stream_id` 发送给上游。

### 续接

将返回的 `resp_monoize_` id 作为 `previous_response_id` 发送。Monoize 随后用缓存的输入、缓存的输出和新输入构造请求。`store=false` 时同样可用。

- 每个 lane 缓存最后一个 `completed`、`incomplete` 或 `cancelled` 响应，包括被中断和被引导的响应。
- `previous_response_id` 可以指向其他 lane 的响应。用这种方式可以分叉会话。
- v2 的 `response.create` 只使用自身的控制参数。只有 v1 的 `response.append` 继承缓存响应的控制参数。
- 以 `response.failed` 或错误帧结束的轮次不创建缓存项，还会删除同一 lane 续接所引用的缓存项。失败的分叉保留父缓存项。
- 未知 id 返回 `previous_response_not_found`，连接保持打开。收到该错误后，请重新发送完整历史。
- `previous_response_id` 不是字符串，或与 `conversation` 同时出现时，返回 `400 invalid_request`。
- Monoize 将 `item_reference` 输入替换为匹配缓存项的副本。未匹配的引用原样转发。
- 关闭 WebSocket 会删除所有缓存响应。

### 预热

在 `response.create` 上将 `generate` 设为 `false` 可预热会话。

- 如果第一次尝试可以使用上游 WebSocket，Monoize 把预热发送给上游。计费和日志使用上游用量。
- 否则 Monoize 在本地返回 `response.created` 和 `response.completed`，不调用上游，不写日志行，也不计费。

### 中断

发送 `{"type":"response.interrupt"}`。可选成员为 `response_id`、`stream_id` 和 `mode`。`mode` 只接受 `discard_partial_items`。

- `response_id` 选择对应的生成中轮次。否则 `stream_id` 选择 lane，没有 `stream_id` 时选择默认 lane。
- 所选 lane 空闲时，中断不执行操作。对同一轮次的重复中断只产生一次中断。
- 中断不消耗轮次，也不创建日志行。
- 如果 `response_id` 不对应生成中轮次，而其他轮次正在生成，Monoize 发送 `response.interrupt.failed`，错误码为 `response_not_in_progress`。
- 使用上游 WebSocket 时，Monoize 向上游发送一次中断。它用公开 id 转发 `response.interrupt.accepted` 或 `response.interrupt.failed`，然后转发终态事件。
- 使用 HTTP SSE 或非 Responses 上游时，Monoize 在 `response.created` 之后停止转发。它发送 `response.interrupt.accepted`，然后发送 `response.completed`，其中只含已完成的条目，`usage` 为 `null`。
- 此时 Monoize 在后台读完剩余的上游响应。计费和日志行只完成一次。
- 客户端断开后，Monoize 丢弃排队的轮次，并中断上游 WebSocket 响应。它继续读取终态用量用于计费。HTTP 上游继续读取响应。

### 中途引导（steering）

发送 `{"type":"response.steer","previous_response_id":"<id>","input":"..."}` 可向生成中的响应追加输入。`input` 是字符串，或非空的 `user` 消息数组。steer 不进入队列，也不消耗轮次。

Monoize 通过上游 WebSocket 转发 steer，并用公开 id 转发 `response.steer.accepted`、`response.steer.pending` 和 `response.steer.failed`。

steer 被接受后，上游可以启动后继响应。Monoize 将其作为新轮次运行，它有独立的 id、日志行和计费，`previous_response_id` 指向被引导的响应。如果 Channel 或上游模型不再匹配，该轮次以 `502 steer_successor_unavailable` 失败。

`response.steer.failed` 使用以下错误码：

| 错误码 | 含义 |
| --- | --- |
| `invalid_input` | 事件有多余成员，或 `input` 无效 |
| `response_not_active` | 缓存的响应已不在生成中 |
| `response_not_found` | id 不匹配此连接上的任何响应 |
| `steering_not_supported` | 轮次使用 HTTP SSE 或非 Responses 上游，或该 Channel 之前拒绝过 steer |

Monoize 会记住拒绝 steer 的 Channel，直到进程重启。此后对该 Channel 的 steer 在本地失败。当前响应继续生成。

### 错误帧与限制

每个错误帧都使用以下结构，不带 `sequence_number`。命名 lane 的错误还带 `stream_id`。轮次错误只结束该轮次。

```json
{ "type": "error", "status": 400, "error": { "type": "invalid_request_error", "code": "previous_response_not_found", "message": "...", "param": "previous_response_id" } }
```

| 错误码 | 状态码 | 含义 |
| --- | --- | --- |
| `invalid_websocket_event` | `400` | 消息无效。第一条消息无效时还会关闭连接 |
| `invalid_stream_id` | `400` | `stream_id` 格式无效 |
| `websocket_stream_limit_reached` | `400` | 事件指定了第 33 个 lane |
| `invalid_interrupt` | `400` | `mode` 的值不受支持 |
| `background_not_supported` | `400` | 事件设置了 `background=true` |
| `websocket_history_limit_exceeded` | `400` | 组装后的请求超过保留历史限制 |
| `websocket_connection_limit_reached` | `400` | 连接达到轮次、字节或时长限制，Monoize 随后关闭连接 |
| `websocket_sse_limit_exceeded` | `502` | 内部 SSE 帧或缓冲区限制结束了该轮次 |

连接在达到时长限制时关闭，默认为 60 分钟。请打开新连接继续。所有限制参见[配置](/zh/docs/configuration)。

## 关闭推理

在 Chat Completions 请求中设置 `"reasoning_effort": "none"`。在 Responses 请求中设置 `"reasoning": { "effort": "none" }`。

Monoize 向 Responses 上游以及 `openai`、`openrouter`、`vercel`、`generic` Chat 方言保留显式 `none`。在 `openrouter`、`vercel` 和 `generic` 上，如果 Chat 请求保留了原生 `reasoning` 对象，Monoize 会在该对象中写入 `effort: "none"`，不再发送顶层简写字段。

如果没有显式 Messages 控制参数，Messages 上游收到的内容取决于模型：

- 多数模型收到 `thinking: { "type": "disabled" }`。
- Sonnet 5.5 收到 `thinking: { "type": "between_tools" }`。
- 其他拒绝 `disabled` 的模型（例如 Fable、Mythos、Opus 5.5 及以上）不会收到 `thinking` 字段。

Gemini 上游收到对应模型系列的关闭值：

- 预算系列收到 `thinkingBudget: 0`。Gemini 2.x Pro 无法关闭思考，因此收到 `128`。
- 等级系列（例如 Gemini 3 和 4）收到支持的最低 `thinkingLevel`。
- 不支持思考的系列不会收到思考配置。

`deepseek` Chat 方言在 `none` 时收到 `thinking: { "type": "disabled" }`，不带 `reasoning_effort`。其他力度值作为 `reasoning_effort` 透传。

省略推理力度会允许上游使用默认值。请选择支持关闭推理的模型。强制推理的模型无法满足此请求。

## Anthropic Messages

```bash
curl http://localhost:8080/v1/messages \
  -H "x-api-key: sk-..." \
  -H "anthropic-version: 2023-06-01" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "my-model",
    "max_tokens": 1024,
    "messages": [{ "role": "user", "content": "Hello" }]
  }'
```

在 `messages` 上游上，Monoize 转发客户端的 `anthropic-version` 值，没有时发送 `2023-06-01`。它把客户端的 `anthropic-beta` 令牌与生成的令牌和 Channel 令牌合并，每个令牌只出现一次。其他上游类型不会收到这些客户端请求头。

Monoize 转发显式的 `thinking` 和 `output_config` 控制参数，不做本地校验，由上游决定是否接受。Monoize 只校验自己生成的控制参数，组合无效时返回 `400 invalid_request`。

每个 `/v1/messages` 和 `/v1/messages/count_tokens` 响应都带 `request-id` 响应头。格式见错误响应一节。

### 统计 Token

`POST /v1/messages/count_tokens` 的认证、重定向和模型限制与 `/v1/messages` 相同。

- Monoize 按路由顺序只尝试 `messages` Channel，转发请求体时只替换 `model`。
- 没有这类 Channel 时返回 `404 not_found_error`。Claude Code 随后改用本地估算。
- 此端点不计费，不写请求日志，也不改变 Channel 健康状态。

## Gemini 上游

将 Channel 的上游类型设为 `gemini`，即可通过现有端点使用 Gemini。此支持不新增公开的 Gemini HTTP 端点，也不包含 Live API。

Monoize 双向转换 `generateContent` 请求、响应和对话历史。流式响应使用 `streamGenerateContent` SSE。

- 文本、推理、函数调用、函数结果和支持的媒体保留顺序与标识。
- 其他协议把文本和媒体上的思考签名作为不透明推理值携带。原样重放这些值，即可把每个签名还原到对应 Part。
- 在 Gemini 3 及以上版本中，当前轮次每个 model Content 的第一个无签名函数调用会收到 `skip_thought_signature_validator`。
- Channel base URL 可以以 `/v1`、`/v1beta` 或 `/v1alpha` 结尾，该路径段决定 API 版本。否则 Monoize 使用 `v1beta`。
- 推理控制参数取决于模型系列。Gemini 2.x 使用限制在模型范围内的 `thinkingBudget`。Gemini 3 及以上使用 `thinkingLevel`。Monoize 不会同时发送两者。
- 自定义工具转为只有一个 `input` 字符串的函数声明。Monoize 把返回的调用还原为自定义工具调用。
- 生成控制参数、结构化响应格式、工具和工具选择转换为目标协议支持的对应字段。
- 超过 5 个停止序列时，该次尝试以请求错误失败。
- Token logprobs 始终关联匹配的文本。文本变更后会丢弃失效的分数。Gemini 最多允许请求 20 个 top logprobs。
- 可表示的引用和 grounding 来源链接转换为目标格式。引用范围保留文本中的位置，包括非 ASCII 文本。
- 文本和推理在完成前持续输出。需要完整内容的媒体和带签名的 Part 可以等到完成后输出。失败或截断的流返回错误。
- Monoize 优先返回 index 为 0 的候选响应，否则返回第一个候选响应。独立候选响应不会合并。

其他协议按以下方式接收 Gemini 专属输出：

- 代码执行 Part 显示为带围栏的 assistant 文本。
- `toolCall` 和 `toolResponse` Part 完整保存在不透明推理值中。客户端重放该值时，Monoize 将其还原到原位置。丢弃推理值的客户端会丢失它们。
- 其他未知 Part 和无法转换的元数据仅在 Gemini 内保留。

### 续写令牌

`CONTINUATION` 结束原因产生原因为 `max_output_tokens` 的不完整响应。所有协议都以不透明推理值接收令牌。Responses 客户端还能看到 `incomplete_details.continuation_token`。

- 要继续生成，请带着该值重放不完整的 assistant 轮次。Monoize 会移除该轮次，并把最新令牌作为 `continuationToken` 发送。
- 客户端也可以重复原始内容，并显式传入顶层 `continuationToken`。
- `maxOutputTokens` 在多次续写之间累计。每次续写都应调大或省略它。

### 图像尺寸

生成图像时，Monoize 把 `WxH` 尺寸转换为 `imageConfig.aspectRatio` 和 `imageConfig.imageSize`。原生值优先。

- 宽高比取模型系列支持的最接近比例。
- 最长边决定档位：不超过 792 为 `512`，不超过 1584 为 `1K`，不超过 3168 为 `2K`，更大为 `4K`。
- Monoize 将档位提高到模型文档列出的最小可用档位；没有时降到其最大档位。
- 2.5 Flash Image 和 3.1 Flash Lite Image 不接收 `imageSize`。
- 3.1 Flash Image 文档列出 `512`、`1K`、`2K`、`4K`。Nano Banana 和 3 Pro Image 文档列出 `1K`、`2K`、`4K`。

## 跨协议的内置工具

内置工具路由到其他上游协议族时不会产生请求错误。有目标映射时，Monoize 转换定义。否则在该次尝试中丢弃定义。

| 来源工具 | 目标上游 | 结果 |
| --- | --- | --- |
| Responses `web_search`、`web_search_preview` | `messages` | `web_search_20250305`，复制 `allowed_domains` 和 `user_location` |
| Messages `web_search_*` | `responses` | `web_search`，复制 `allowed_domains` 和 `user_location`，丢弃 `blocked_domains` 和 `max_uses` |
| 两个协议族的网页搜索 | `chat_completion`，`openrouter` 方言 | `openrouter:web_search` |
| 两个协议族的网页搜索 | `chat_completion`，其他方言 | 丢弃 |
| `web_search*` | `gemini` | `googleSearch` |
| `code_interpreter`、`code_execution*` | `gemini` | `codeExecution` |
| `web_fetch*` | `gemini` | `urlContext` |
| 其他所有内置工具 | 其他协议族 | 丢弃 |

- 强制选择已映射的工具时，选择仍然是强制的。
- 指向已丢弃工具的选择变为 `auto`。没有剩余工具时，Monoize 移除 `tool_choice`，也不发送 `tools: []`。
- 搜索结果条目不跨协议族。客户端收到回答文本，但没有搜索块。
- Chat 客户端可以发送 `openrouter:*` 工具。Monoize 在 `openrouter` 和 `generic` 方言上原样重放。
- 在 `openai`、`deepseek` 和 `vercel` 方言上，这些工具在发送前以 `400 unsupported_tool` 失败。其他没有 Chat 编码的工具类型同样失败。

## 跨协议的缓存断点

Monoize 在三种客户端协议的请求块上都接受 `cache_control` 和 `prompt_cache_breakpoint`。同一块同时带两者时，`cache_control` 优先。转换时，标记保留在文本、媒体、工具调用、工具结果和工具定义对象上。顶层 `cache_control` 仍是 Messages 请求控制参数。

| 上游 | 发送的标记 |
| --- | --- |
| `messages` | 对应块或工具上的 `cache_control` |
| `responses` | 输入文本、图像、文件和工具输出部分上的 `prompt_cache_breakpoint` |
| `chat_completion`，`openai` 方言 | 内容部分上的 `prompt_cache_breakpoint` |
| `chat_completion`，`openrouter`、`vercel`、`generic` 方言 | 内容部分和工具定义上的 `cache_control` |
| `chat_completion`，`deepseek` 方言 | 无。DeepSeek 自动缓存 |
| `gemini` | 无 |

来自同一协议族的标记原样重放。转换后的标记遵循以下规则：

- 丢弃未知成员。只有目标接受时才保留 `ttl`，Monoize 不会换算 TTL。
- `cache_control` 接受 `5m` 和 `1h`。Responses 的 `prompt_cache_breakpoint` 接受 `30m` 和 `12h`。`openai` Chat 接受 `30m`。
- 转换到 Responses 或 `openai` Chat 需要 GPT-5.6 及以上的模型 id。使用其他名称的部署别名不会收到标记。
- Responses 和 `openai` Chat 不会在 assistant 文本、工具调用或工具定义上收到转换后的标记。带标记的 system 消息转为输入消息。
- 工具结果上的转换标记移到其最后一个可用部分。
- 转换到 `messages` 时，Monoize 丢弃空文本上的标记。它保留最后若干个标记，数量上限为 4 减去顶层 `cache_control` 和 Provider 条目中的原生标记。

## 决策

决策模型用概率回答类型化问题，不生成文本。Monoize 接受两种请求格式：

| 端点 | 请求格式 |
| --- | --- |
| `POST /v1/systemone` | System One：`state` 加 `questions` 对象，题型为 `noul`、`choice`、`score` |
| `POST /v1/decisions` | OpenAI Decisions：`input` 加 `questions` 数组，题型为 `predicate`、`choice`、`score` |

```bash
curl http://localhost:8080/v1/systemone \
  -H "Authorization: Bearer sk-..." \
  -H "Content-Type: application/json" \
  -d '{
    "model": "my-decision-model",
    "state": "My payouts have failed for 3 days.",
    "questions": {
      "urgent": { "type": "noul", "instructions": "Is this request urgent?" },
      "team": {
        "type": "choice",
        "instructions": "Which team owns this request?",
        "criteria": { "billing": "Payments and refunds", "technical": "Bugs and outages" }
      }
    }
  }'
```

这两个端点只路由到 `system_one` 和 `openai_decisions` 类型的 Channel。其他端点不会路由到这两种 Channel。每个决策端点都可以使用这两种 Channel。决策端点不支持流式。

请求格式与 Channel 格式相同时，Monoize 转发全部字段，只替换 `model`。格式不同时，Monoize 转换请求和答案：

- 文本输入可双向转换。对象或数组形式的 `state` 转为 `input` 中的 JSON 文本。
- 图片输入需要 `openai_decisions` Channel。如果没有这种 Channel 服务该模型，Monoize 返回 `400 unsupported_decision_input`。
- `noul` 的 criteria 追加到 `predicate` 的 instructions 末尾。布尔型 choice 值转为 System One 键 `"true"` 和 `"false"`。
- OpenAI 的 `refusal` 答案在 System One 响应中变为 `{ "type": "refusal" }`。
- 目标格式未定义的字段会被丢弃，例如 `safety_identifier`。

计费使用上游返回的 `usage.input_tokens` 和 `usage.output_tokens`。决策上游不对输出 token 收费，但部分上游会报告输出 token。请把每个决策模型的输出价格设为 `0`。

## 图像

生成：

```bash
curl http://localhost:8080/v1/images/generations \
  -H "Authorization: Bearer sk-..." \
  -H "Content-Type: application/json" \
  -d '{
    "model": "my-image-model",
    "prompt": "A lighthouse at dawn",
    "size": "1024x1024"
  }'
```

使用 `multipart/form-data` 上传图片文件：

```bash
curl http://localhost:8080/v1/images/edits \
  -H "Authorization: Bearer sk-..." \
  -F model="my-image-model" \
  -F prompt="Add a red boat" \
  -F 'image[]=@input.png'
```

添加 `-F mask=@mask.png` 可使用 PNG 蒙版。编辑请求接受 1–16 张源图片和最多一个蒙版。

使用 JSON 提交图片引用：

```bash
curl http://localhost:8080/v1/images/edits \
  -H "Authorization: Bearer sk-..." \
  -H "Content-Type: application/json" \
  -d '{
    "model": "my-image-model",
    "prompt": "Add a red boat",
    "images": [{ "image_url": "https://example.com/input.png" }],
    "mask": { "image_url": "https://example.com/mask.png" }
  }'
```

每个 `images` 条目和可选的 `mask` 对象必须恰好包含一个 `image_url` 或 `file_id`。`image_url` 接受 HTTP(S) URL 或 Base64 数据 URL。文件 ID 必须能通过所选上游凭据访问。文件 ID 不会在上游账号或 Provider 之间转移文件。

两个端点都要求提供 `model` 和 `prompt`。非流式请求的 `n` 仍会拆分为独立子请求。设置 `stream=true` 和 `n=1` 可接收图像 SSE 事件。原生 `openai_image` 路由将内联图片作为 multipart 发送。只要任一输入或蒙版保留 HTTP(S) URL 或文件引用，该路由就使用 JSON。

设置 `stream=true` 后，Monoize 立即发送 SSE 保活注释，并在连续 15 秒没有数据事件时再次发送。OpenRouter 图片编辑自动使用非流式上游请求；其他路由收到明确拒绝流式的 HTTP 400 或 422 后，只回退一次。JSON 图片响应转换为完成事件，不会伪造预览图。计费和日志仍计为一次流式请求，普通网络错误不会触发此回退。这可以在生成期间保持下游连接，但不会延长上游请求超时。

对于 Responses 路由，配置 [image_enable_openai_generation_tool](/zh/docs/transforms/image_enable_openai_generation_tool)。请求中的图像参数优先于变换默认值，蒙版会映射到工具的 `input_image_mask`。图像 `background` 用于配置工具，与 Responses 的布尔值 `background` 不同。Responses 路由会明确拒绝图像 `style` 和 `response_format="url"`。

图像响应保留上游返回的 `quality`、`size`、`background`、`output_format` 和图像 `model`。上游未返回的值保持缺省；请求参数不能证明上游的实际执行结果。上游明确返回的 `mime_type` 或 `media_type` 会在 `output_format` 缺省时写入 `output_format`。每张返回的图像都包含 `mime_type`。返回多张图像时，只有所有图像都报告相同值，响应才会包含对应的顶层字段。图像流的完成事件携带各自图像的元数据。

## 错误响应

响应开始前的错误使用所调用端点的 HTTP 状态码和 JSON 响应体。无论 `stream` 为 `true` 还是 `false`，此规则都适用。Monoize 不会把这些错误包装成 HTTP `200` 或 SSE。

`POST /v1/responses` 和 `POST /v1/chat/completions` 返回以下响应体：

```json
{ "error": { "message": "...", "type": "invalid_request_error", "param": null, "code": "invalid_value" } }
```

`POST /v1/messages` 返回以下响应体，并在 `request-id` 响应头中返回相同的 id：

```json
{ "type": "error", "error": { "type": "invalid_request_error", "message": "..." }, "request_id": "req_..." }
```

Embeddings、compact、决策和图像端点遵循相同的状态码规则，并保留 `{"error": ...}` 响应体。

### 本地错误

| HTTP 状态码 | 错误码 | 含义 |
| --- | --- | --- |
| `400`、`413`、`415`、`422` | `invalid_json` | 请求体不是有效 JSON、过大、内容类型不是 JSON，或结构错误 |
| `401` | `unauthorized` | API 密钥缺失、无效、被禁用或已过期 |
| `402` | `insufficient_balance` | 用户或子账户余额不足 |
| `403` | `model_not_allowed` | 密钥的模型限制拒绝了请求的模型 |
| `403` | `ip_not_allowed` | 客户端 IP 不在密钥的 IP 白名单中 |
| `502` | `upstream_error` | 没有路由服务该模型 |

### 上游失败

所有路由都失败时，客户端收到最后一次失败尝试的状态码、`type`、`code`、`param` 和脱敏后的 `message`。

- `400`、`404`、`409`、`413`、`422`、`429` 和 `5xx` 等状态码原样透传。
- 最后一次上游返回 `401`、`403` 或 `407` 时，客户端收到 `502`，错误码为 `upstream_error`。这类失败属于 Channel 凭据，与客户端无关。
- 该响应体还带 `upstream_status`，上游报告错误码时还带 `upstream_code`。`type` 为 `server_error`，Messages 上为 `api_error`。
- 没有上游 HTTP 状态码的失败返回 `502`。传输失败的消息为 `failed to request upstream`。
- 没有上游错误码的失败使用 `upstream_error`。
- 客户端自身的 Monoize 密钥导致的 `401` 仍为 `401`。

在 `/v1/messages` 上，`error.type` 始终是 Messages 原生错误类型。`request_id` 的值是 `req_` 加请求 ID。已经以 `req_` 开头的 id 保持不变。

### 流开始后的错误

Monoize 在上游尝试被接受后发送 SSE 响应头。之后的失败无法改变 HTTP 状态码 `200`，因此在流中返回：

- `/v1/chat/completions` 发送一个错误数据帧，然后发送 `data: [DONE]`。
- `/v1/responses` 发送扁平的 `error` 事件，包含 `code`、`message` 和 `param`，没有 `[DONE]`。
- 上游的 `response.failed` 仍为 `response.failed`，保留部分输出和用量。
- `/v1/messages` 发送带 `request_id` 的 `error` 事件，没有 `[DONE]`。

### 限流响应头

在同协议族路由上，Monoize 转发 `retry-after`、`retry-after-ms`、`x-should-retry`、`anthropic-ratelimit-*` 和 `x-ratelimit-*`，错误和成功响应都适用。跨协议族路由和上游 WebSocket 尝试不转发这些响应头。

### 脱敏的错误文本

系统设置 `monoize_mask_sensitive_info` 默认开启。开启时，Monoize 会遮蔽客户端错误文本中的 URL、主机名、IPv4 地址和 `api_key:` 值。

- 例如，`api.openai.com` 变为 `***.***.com`。
- Monoize 始终遮蔽 Channel `base_url`、Channel `proxy_url` 和节点代理的主机。
- `response.create`、`reasoning.effort`、`messages.1.content.0.type` 等协议标识符保持可读。
- 未配置的私有名称如果最后一段未知，可能仍然可见。
- 传输失败只显示 `failed to request upstream`。无法解析的上游响应体只显示状态码。

完整详情请在[请求日志](/zh/docs/request-logs)中查看。
