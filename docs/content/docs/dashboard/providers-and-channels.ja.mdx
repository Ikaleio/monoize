## 概念

- **Provider** はルーティンググループです。ルーティング順序、リトライ予算、ヘルスポリシー、順序付き変換チェーンを定義します。
- **Channel** は Provider 内の 1 つの上流エンドポイントです。上流タイプ、ベース URL、認証情報、モデル対応付け、重み、タイムアウトを保持します。

リクエストはまず Provider を選択し、その中の Channel を選択します。選択規則は[ルーティングと信頼性](/ja/docs/routing)を参照してください。

![Provider 一覧](/images/en/providers.webp)

## リアルタイム使用量

各 Provider 行には直近 60 秒の RPM と TPM が表示されます。ページの表示中は 10 秒ごとに更新します。
RPM は、全ユーザーの保存済みリクエストをすべての終了ステータスで集計します。TPM は入力と出力の token 数の合計です。
キャッシュや推論の token を重複して加算しません。処理中のリクエストとリトライ履歴の各試行は集計しません。
対象がない場合は `0`、指標を取得できない場合は `—` を表示します。
各 Provider 行には順位とリトライ方針が表示されます。各 Channel 行には 1 つの状態、モデル数、重みの割合が表示されます。

## Provider を作成

1. サイドバーの **Provider** を開きます。
2. **Provider を追加**をクリックして名前を入力します。
3. 既定値が合わない場合は**ルーティング**セクションでリトライオプションを調整します。
   - **Provider の試行回数**：**利用可能なすべての Channel を試行**（既定、`max_retries = -1` として保存）または**回数を指定** N（`max_retries = N - 1` として保存）。
   - `channel_max_retries`：次へ進む前の Channel 内リトライ回数。既定 `0`。
   - `channel_retry_interval_ms`：Channel 内リトライの間隔。既定 `0`。
4. 明確な理由がない限り、`circuit_breaker_enabled` は有効のままにします。

## Channel を追加

1. Provider を開き、**Channel を追加**をクリックします。
2. 上流タイプを選択します：`responses`、`chat_completion`、`messages`、`gemini`、`openai_image`、`openrouter_image`、`replicate`、`system_one`、`openai_decisions`。
3. 上流のベース URL と API キーを入力します。
4. 重みを設定します。トラフィックは対象 Channel 間で重みに比例して分配されます。既定 `1`。
5. 必要に応じて、**ルーティングアフィニティ**で**送信プロキシ**の URL を入力します。空欄の場合はノードのプロキシを使います。

`http://`、`https://`、`socks5://`、`socks5h://` を使用できます。`socks5` では Monoize が上流のホスト名を解決し、`socks5h` ではプロキシが解決します。

認証が必要な場合は `socks5h://user:p%40ss@proxy.example:1080` のように入力します。ユーザー名とパスワードに含まれる予約文字は、`@` を `%40` にするなど、パーセントエンコードしてください。**上流から取得**と **WebSocket を検出**は、編集中のプロキシ URL を使用します。

SOCKS5 で HTTP リクエストを転送するとき、長い認証情報はコネクタのバッファ上限を超える場合があります。デコード後のユーザー名とパスワードの合計上限は、IPv4 で 246 バイト、IPv6 で 234 バイトです。`socks5h` でホスト名を送る場合は、249 バイトからホスト名の長さを引いた値が上限です。

![Channel の送信プロキシ](/images/en/channel-proxy.webp)

後で Channel を編集するとき、API キー欄を空にすると保存済みのキーが維持されます。

無効なフォームを保存すると、エディタはエラーのあるセクションと Channel を開きます。次に該当フィールドへフォーカスを移し、その横にエラーを表示します。必須フィールドには**必須**と表示されます。

## 意思決定モデル

意思決定モデルには `system_one` または `openai_decisions` の Channel を使います。これらの Channel は `/v1/systemone` と `/v1/decisions` だけを提供します。[API エンドポイント](/ja/docs/endpoints)を参照してください。

| 上流 | タイプ | ベース URL |
| --- | --- | --- |
| TypeSafe Jev | `system_one` | `https://api.typesafe.ai` |
| OpenRouter | `system_one` | `https://openrouter.ai/api` |
| OpenAI | `openai_decisions` | `https://api.openai.com` |

Channel テストは、はい・いいえの質問を 1 つだけ含む非ストリーミングの意思決定リクエストを 1 回送信します。上流で料金が発生する場合があります。

## OpenRouter の画像

OpenRouter の画像モデルには **OpenRouter Image**（`openrouter_image`）を選択します。
ベース URL を `https://openrouter.ai/api` に設定します。
論理モデルを上流のモデル ID に対応付けます。例：`openai/gpt-image-2.5-sunburst`。

生成と編集は、どちらも上流の `/api/v1/images` を呼び出します。
Monoize は入力画像を JSON の `input_references` に変換します。
下流では引き続き `/v1/images/generations` と `/v1/images/edits` を使用します。
この Channel タイプは画像マスクとファイル ID 参照に対応していません。

モデル取得では OpenRouter の画像モデル一覧を読み取ります。
Channel テストは非ストリーミングの画像生成リクエストを 1 回送信します。上流で料金が発生する場合があります。
選択したモデルがストリーミングに対応している場合、転送リクエストでも使用できます。
画像編集で `stream=true` を指定すると、Monoize は OpenRouter に非ストリーミングのリクエストを送り、下流の SSE を維持します。
待機中はハートビートコメントを送り、画像の取得後に完了イベントを送ります。

![OpenRouter Image Channel](/images/en/openrouter-image-channel.webp)

## セッションキャッシュヘッダー

Channel で**自動セッションアフィニティ**を設定すると、転送する各リクエストに安定したセッション識別子を付けます。

この設定が `null` のとき、Monoize は次のベース URL で自動的に有効にします。

- Cloudflare Workers AI: `https://api.cloudflare.com/client/v4/accounts/{account_id}/ai`（任意の `/v1`）
- OpenCode Zen または OpenCode Go: `https://opencode.ai/zen` とその配下のパス

有効なとき、Monoize は同じ値で次の 2 つのヘッダーを送ります。

- `x-session-affinity`
- `x-opencode-session`

値の優先順位は次のとおりです。Channel の追加ヘッダーにある上記いずれかの名前、クライアントヘッダー（`session_id`、`session-id`、`x-session-id`、`x-opencode-session`、`x-session-affinity`）、本文の会話 ID、`prompt_cache_key`、最後に会話先頭のハッシュです。

OpenCode Go は `x-opencode-session` でプロンプトキャッシュをセッションに結びます。このヘッダーがないリクエストは失敗することがあります。

OpenCode Zen または OpenCode Go への生存プローブでは、Channel の追加ヘッダーにこれらの名前がないとき、リテラル値 `mono-probe` を送ります。

## Chat ダイアレクト

**API タイプ**が **Chat Completion** のとき、接続セクションで **Chat ダイアレクト** を設定します。ダイアレクトはリクエスト形式を決めます：推論フィールド、最大トークンフィールド、キャッシュマーカー、Provider 拡張。値は `generic`、`openai`、`deepseek`、`openrouter`、`vercel` です。[Chat ダイアレクト](/ja/docs/endpoints#chat-ダイアレクト)を参照してください。

- 新しい Chat Completion Channel の既定値は `generic` です。Monoize は Base URL やモデルからダイアレクトを判定しません。
- `chat_completion` Channel が `chat_dialect` を省略するか `null` を送ると、API は `generic` を保存します。不明な値は `400` を返し、`param` は `channels[i].chat_dialect` です。
- 別タイプの Channel に null 以外の `chat_dialect` を送ると `400` を返します。タイプを Chat Completion から変更すると、エディターは値を消去します。
- **プロトコルの上書き**のルールは、モデル glob で API タイプを選択します。ルールが **Chat Completion** を選択すると、ルール独自の **Chat ダイアレクト** を表示します。一致するモデルでは、Monoize は Channel のダイアレクトの代わりにこの値を使います。
- `chat_completion` ルールが `chat_dialect` を省略するか `null` を送ると、API は `generic` を保存します。別タイプのルールに null 以外の値を送ると `400` を返します。不明な値も `400` を返します。どちらも `param` は `api_type_overrides[i].chat_dialect` です。
- このフィールドを追加するアップグレードは、既存のすべての Chat Completion Channel と上書きルールを `generic` にします。アップグレード後、OpenAI、DeepSeek、OpenRouter、Vercel の各 Channel にダイアレクトを選択してください。これらのベンダーへ向かう Chat Completion 上書きルールにも選択してください。一致したルールのダイアレクトは Channel のダイアレクトより優先されます。

## 上流 WebSocket

**接続** の **API type** の直後に **上流 WebSocket** を置きます。Routing affinity の下に置かないでください。値は次のとおりです。

- `null`（不明）: Responses WebSocket クライアントは先に Upgrade を試します。ハンドシェイク失敗時は、同じ attempt で HTTP SSE を使います。保存値が `null` のときだけ、成功または失敗の結果を書き込めます。
- `true`（対応）: Upgrade を優先します。ハンドシェイク失敗時も HTTP SSE を使います。保存値は変わりません。
- `false`（非対応）: Upgrade しません。

**WebSocket を検出** をクリックすると `GET {base}/v1/responses` をプローブします。結果は下書きに入ります。Provider を保存すると永続化します。HTTP POST クライアント、ヘルスプローブ、Channel 生存テストは HTTP のままです。

## Channel をテスト

Provider を展開し、Channel 行の**モデルを選んでテスト**をクリックします。または保存後に Channel エディターの**テスト**をクリックします。その後、順次テストまたは並行テストを実行します。並行テストは同時に最大 5 件のリクエストを送ります。ダイアログを閉じても結果は残り、実行中のテストはバックグラウンドで続きます。**停止**で中止できます。**失敗分を再テスト**は失敗したモデルだけを再実行します。

Provider を展開すると、Channel 行のスイッチでエディターを開かずにその Channel をすぐ有効化または無効化できます。

テストは出力上限 16 token の短いストリーミング補完を送ります。HTTP 2xx だけでは不十分です。ストリームはプロトコルの終端イベントに到達する必要があります。

Responses Channel では、`response.completed` は合格です。error オブジェクトがない `response.incomplete` も合格です。推論モデルは 16 token 上限に達して `incomplete` を返すことがあります。その結果でも Channel には到達できています。

## モデルを対応付け

複数のモデルを変更するには、**対応モデル**で**選択**をクリックします。次に一覧を絞り込んでモデルを選択し、削除するか倍率をまとめて設定します。モデルピッカーでは現在の結果をすべて選択または解除できます。**手動で追加**には複数のモデル ID を入力できます。

各 Channel は、提供する論理モデルを列挙します。モデルエントリの内容：

- `redirect`：実際の上流モデル名。空にすると論理名をそのまま送信します。
- `multiplier`：課金に使う非負の小数の価格乗数。`0` の場合、この Channel のリクエストは無料です。

Provider 内の有効な Channel が論理モデルを対応付けている場合のみ、そのモデルはその Provider にルーティングされます。

## リモート compact

モデル取得は、上流モデル一覧から Channel の compact 方式を分類します。

- `openai_compact_sibling`：一覧にベース ID と `{base}-openai-compact` の両方があります。それらの兄弟 ID を Channel のモデルマップに残してください。compact リクエストは回線モデルを兄弟モデルに書き換えます。
- `same_model`：そのような組はありません。compact リクエストは会話モデルをそのまま送ります。

上流一覧にない compact 兄弟 ID を作らないでください。

## 課金の上書きを設定

Provider で**価格未設定時の無料精算**と**Usage 欠落時の無料精算**を設定します。各設定は、グローバル値の継承、強制有効、強制無効を選べます。

ツール価格がない場合は常にフェイルオープンします。Monoize は未価格のツールクラスを記録し、そのクラスのツール料金をゼロにします。

## Provider の変換

Provider は順序付き変換ルールのリストを保持できます。Provider の選択後、上流エンコードの前に、その Provider が処理するすべてのリクエストに適用されます。実行順序は Provider → グローバル → API キーで、エディタにもこの順序が表示されます。[変換](/ja/docs/transforms)を参照してください。

## グループ

すべての Provider は少なくとも 1 つのグループに属します。API キーは、グループが交差する Provider のみにルーティングされます。ユーザー層や環境の分離にグループを使います。
