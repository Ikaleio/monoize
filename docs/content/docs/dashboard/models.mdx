## Logical models

Clients request a logical model name. Monoize resolves that name against your Providers and Channels. The name your clients see never has to match an upstream vendor name.

One logical model can map to several Channels across several Providers. This gives you failover and load splitting without client changes.

## Redirects

A Channel model entry can set `redirect` to the real upstream model name.

Example: clients call `my-fast-model`. Channel A redirects it to `gpt-4o-mini`. Channel B redirects it to `claude-3-5-haiku-20241022`. Billing and the request-log model always use the logical name.
The admin log shows the upstream response model only when it differs from the request-log model. The comparison ignores ASCII case.

## Model pricing

The **Model Pricing** page is the pricing console. It has four tabs:

- **Model Pricing**: one price row per model. Each row sets a billing mode: `per_token`, `per_request`, or `tiered_expr`.
  `tiered_expr` can store context-window price steps and a Fast / Priority table.
  Monoize applies Fast prices when the upstream response `service_tier` is `fast` or `priority`.
  It also applies Fast prices when Anthropic `usage.speed` is `fast`.
  A row without its required price shows **Incomplete** and is billed like a missing row.
- **Unpriced Models**: mapped models that have no enabled price row. The tab label shows the count, and each row names the Provider and Channel that serve the model.
- **Tool Prices**: prices for server-side tool classes. Units are `1k_calls`, `minute`, and `session`.
- **Upstream Sync**: price import from Models.dev, OpenRouter, or a new-api instance.

Set each group's billing multiplier on the **Groups** page.

The **Model Marketplace** page lists only models that your group can reach. Each price includes your group's billing multiplier. Admins see all models at base prices.

Monoize computes each charge in this order:

1. Compute the base charge from the model's price row and the recorded usage.
2. Multiply by the group's `billing_ratio`.
3. Multiply by the Channel model entry's `multiplier`.
4. Truncate to a whole number of nano-dollars.

A Channel `multiplier` of `0` makes requests on that Channel free.

Monoize resolves the redirected upstream model first. It falls back to the logical model only for a redirect without an upstream price.

Before each price lookup, Monoize strips at most one recognized suffix from the model ID. Recognized suffixes are reasoning-effort suffixes and `-openai-compact`. Price the base model. Do not add a separate row for `{model}-openai-compact`.

Monoize multiplies the base charge by the Channel model `multiplier` and the routed group's `billing_ratio`. It records the final charge in nano-USD.

By default, Monoize rejects an unpriced model or a response without required Usage. Set the global free-settlement flags or a Provider override only when zero settlement is acceptable.

## Price sync

1. Open **Model Pricing → Upstream Sync**.
2. Select a source: Models.dev, OpenRouter, or a new-api instance.
3. Click **Preview**. The dialog lists added and updated rows as `field: old → new`. Use the filter to show deleted or skipped rows.
4. Click **Apply N changes** in the preview dialog. Monoize applies exactly the previewed changes and records an audit row. When the preview deletes rows, confirm the delete count first.

A preview stays valid for 10 minutes. If it expired, or if prices changed after it, preview again.

Models.dev sync writes context-window price steps and Fast mode prices into `billing_expr`.

Sync does not change a locked field. Sync does not delete rows that you created manually.

Automatic sync is enabled by default. Monoize starts one cycle at process startup and
then runs every 24 hours. Each cycle syncs Models.dev first. It then uses OpenRouter to
add models that Models.dev does not provide. Disable **Automatic price sync** to stop
future cycles.

## Model listing

`GET /v1/models` returns the logical models available to the calling API key. The result reflects key model restrictions and group membership.

## Model globs

Transform rules and some restrictions accept model glob patterns:

- `*` matches any sequence of characters, including an empty one.
- `?` matches exactly one character.
- Matching is case-sensitive and anchored to the full model name.

Example: `gpt-4*` matches `gpt-4o` and `gpt-4o-mini`. It does not match `o4-mini`.
