## API キーの役割

クライアントは API キーで転送リクエストを認証します。すべてのキーは `sk-` で始まります。キーは次のいずれかのヘッダーで送信します。

```bash
Authorization: Bearer sk-...
# または
x-api-key: sk-...
```

有効なキーのないリクエストは HTTP `401` を受け取ります。

![API キー管理](/images/en/api-keys.webp)

## キーの作成

1. サイドバーの**トークン管理**を開きます。
2. 作成ボタンをクリックし、名前を入力します。
3. 必要なオプションを設定します。すべてのオプションに安全なデフォルト値があります。
4. 完全なキーをコピーします。一覧には後からも完全なキーが表示されます。Monoize のキーは一度きりの表示ではありません。

## キーのオプション

| オプション | 効果 | デフォルト |
| --- | --- | --- |
| 有効期限 | 期限を過ぎるとキーは動作を停止します。 | 無期限 |
| 有効化 | 無効化したキーは直ちに認証に失敗します。 | 有効 |
| モデル制限 | 有効にすると、キーは列挙したモデルパターンのみ呼び出せます。 | 無効 |
| IP ホワイトリスト | 設定すると、リクエストは列挙した IPv4/IPv6 アドレスまたは CIDR 範囲からのみ許可されます。 | 空 |
| グループ | キーはグループが交差する Provider にのみルーティングされます。 | ユーザーのグループを継承 |
| 倍率上限 | 価格倍率がこの値を超える Channel モデルエントリをスキップします。 | 上限なし |
| サブアカウント残高 | 有効にすると、キーはユーザー残高ではなく自身の残高を消費します。 | 無効 |
| リクエストキャプチャ | `off`、`capture-all`、`capture-only-abnormal`。[リクエストログ](/ja/docs/request-logs)を参照してください。 | `off` |

## モデル制限

モデル制限のエントリは正確な論理モデル名です。どのエントリとも一致しないモデルのリクエストは HTTP `403`（エラーコード `model_not_allowed`）を受け取ります。

## モデルリダイレクト

キーは順序付きのモデルリダイレクトルールを保持できます。各ルールの内容は次のとおりです。

- `pattern`: 正規表現。Monoize は完全なモデル名に対して `^(pattern)$` として固定一致させます。
- `replace`: リテラルのターゲットモデル名。

最初に一致したルールが、ルーティング・課金・モデル制限チェックの前にモデル名を書き換えます。キーのルールはグローバルルールより先に実行されます。リダイレクトを使うと、クライアントを変更せずにトラフィックを新しいモデルへ移せます。

## グループ

- **ユーザーグループを継承**（デフォルト）: キーは所有ユーザーのグループに従います。
- **明示的なグループ**: 1 つ以上のグループを選択します。順序に意味があります。Monoize は先頭に近いグループの Provider を優先します。[ルーティングと信頼性](/ja/docs/routing)を参照してください。

## キー単位の変換ルール

キーは順序付きの変換チェーンを保持できます。キー単位の変換には安全境界があり、API キースコープで許可された変換タイプのみ受け付けます。[変換ルール](/ja/docs/transforms)を参照してください。
