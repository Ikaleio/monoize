## 路由选择

存在有效订阅时，Monoize 在选择 Provider 前，将密钥分组与订阅分组取交集，并保留密钥分组顺序。
请求不能使用交集之外的 Provider。

对每个请求，Monoize 按以下顺序解析路由：

1. **模型重定向。** 先执行 API 密钥规则，再执行全局规则。第一条匹配的规则重写模型名。
2. **Provider 选择。** Monoize 收集满足以下条件的已启用 Provider：至少有一个已启用、权重大于零的 Channel 服务该模型，且分组与密钥分组有交集。分组顺序决定优先顺序；同一分组内按 Provider 优先级排序。
3. **Channel 选择。** 在选中的 Provider 内，Monoize 按权重随机排序候选 Channel。Channel $i$ 被首先尝试的概率为：

```math
P(i) = \frac{w_i}{\sum_{j=1}^{n} w_j}
```

因此权重为 `2` 的 Channel 获得的流量是权重为 `1` 的 Channel 的两倍。

## 重试与回退

Monoize 按嵌套顺序尝试路由：先在一个 Provider 内遍历 Channel，再前进到下一个 Provider。

- 每个 Channel 获得 `channel_max_retries + 1` 次尝试。默认为 1 次尝试，不做 Channel 内重试。
- `channel_retry_interval_ms` 在 Channel 内重试之间插入等待。默认为 `0`。
- `max_retries` 限制整个 Provider 的总尝试次数。
- 一个 Provider 耗尽后，Monoize 继续尝试下一个符合条件的 Provider。
- 所有 Provider 都耗尽后，客户端收到最后一次失败尝试的状态码和错误。参见[错误响应](/zh/docs/endpoints)。
- 最后一次上游返回 `401`、`403` 或 `407` 时，客户端收到 `502`，错误码为 `upstream_error`。没有任何尝试的请求同样返回 `502 upstream_error`。

### 哪些错误会重试同一 Channel

| 错误 | 同 Channel 重试 | 前进到下一路由 |
| --- | --- | --- |
| 内置分类和最终分类都不是持久性故障的 HTTP `408`、`429`、`5xx` | 是 | 是，Channel 预算耗尽后 |
| 超时、连接被拒绝或重置 | 是 | 是，Channel 预算耗尽后 |
| 内置分类或最终分类为持久性上游故障 | 否 | 是，立即前进 |
| 其他上游错误（如 `400`、`401`、`404`） | 否 | 是，立即前进 |
| 上游协议无法表示请求中的媒体内容 | 否 | 是，立即前进 |
| Monoize 的其他错误（如认证、余额、请求校验、请求编码或计费错误） | 否 | 否；路由终止 |

## 流式保证

Monoize 在第一个上游尝试被接受后发送 SSE 响应头。HTTP 尝试在收到 `2xx` 状态码时被接受。上游 WebSocket 尝试在收到第一个非 Provider 控制事件时被接受。此前的失败返回原生 JSON 错误，而不是 SSE。

发送响应头后，回退继续有效，直到第一个协议数据或错误事件。Monoize 缓冲响应开始事件和 Provider 控制事件（例如 `codex.rate_limits`），直到第一个输出事件。缓冲区最多容纳 256 个事件。SSE 心跳在响应头之后开始，不会结束回退。

如果响应头发送后所有路由都失败，错误会在流中返回，因为 HTTP 状态码已经是 `200`。第一个协议事件之后，Monoize 绝不切换。因此可见的流始终来自同一次生成。

## 熔断器

每个 Provider 都有 `circuit_breaker_enabled` 开关。设为 `false` 后，Monoize 不再依据或跟踪该 Provider 的健康状态，也不再发起主动探测。主动探测没有独立的开关。

仪表盘显示三种 Channel 健康状态：

- **健康。** Channel 满足其他路由条件时，可以接收流量。
- **不健康。** 在 Channel 恢复前，Monoize 不会向它转发任何请求。
- **已禁用。** `enabled` 为 `false`。无论是否开启熔断器，Channel 都不会接收流量。

启用熔断器后，持久性故障会立即使 Channel 变为不健康。对于暂时性故障和限流错误，默认在 30 秒内累计 3 次失败就会触发熔断。启用 `per_model_circuit_break` 后，Monoize 会分别跟踪 Channel 中各模型的健康状态。某个模型不健康时，不影响同一 Channel 中其他模型接收流量。

### 故障分类

Monoize 先按列表顺序检查 `monoize_failure_classification_rules`，再执行内置分类。第一条匹配的规则决定最终类别。规则适用于转发、主动探测和 Channel 测试中的上游错误，包括 HTTP 错误以及上游在成功响应的响应体或流中报告的错误。Monoize 自身的错误和传输故障不参与匹配。

规则要求两个字段都匹配：

- `status_codes`：列表必须包含上游实际返回的 HTTP 状态码。HTTP `200` 流中的错误按 `200` 匹配。空列表匹配任意状态码，也包括没有 HTTP 状态码的上游错误。
- `keyword`：去除首尾空白的关键词必须出现在上游错误的 `message`、`code` 或 `type` 中。Monoize 分别检查每个字段，不区分大小写。比较使用 Unicode 简单小写映射，不按语言环境转换，也不做规范化。

从未保存此设置时，Monoize 按顺序使用以下规则：

| `status_codes` | `keyword` | `class` |
| --- | --- | --- |
| `[503]` | `no available account` | `persistent` |
| `[]` | `no credits remaining` | `persistent` |
| `[503]` | `no available gemini accounts` | `persistent` |
| `[503]` | `no available openai accounts` | `persistent` |
| `[503]` | `no available grok accounts` | `persistent` |
| `[503]` | `no available compatible accounts` | `persistent` |
| `[502]` | `upstream authentication failed` | `persistent` |
| `[502]` | `upstream access forbidden` | `persistent` |
| `[429]` | `额度已用完` | `persistent` |

这些默认规则覆盖 sub2api 等中转服务的密钥级错误。没有这些规则时，这些错误会被判为暂时性或限流故障。`429` 窗口限额（例如 `api key 5小时限额已用完`）不匹配，仍按限流处理。

保存的列表会替换全部默认规则。保存空列表可仅使用内置分类。在[系统设置](/zh/docs/dashboard)中编辑列表。

如果没有规则匹配，Monoize 按以下顺序采用第一条匹配的内置规则。比较上游错误的 `code` 和 `type` 时，先去除首尾空白，再忽略 ASCII 字母的大小写。

1. `persistent`：上游额度耗尽，即使返回 HTTP `429`。错误标识包括 `insufficient_quota`、`credit_balance_exhausted`、`credit_balance_too_low`、`insufficient_balance` 和 `billing_hard_limit_reached`。
2. `rate_limited`：其他 HTTP `429`，包括带有 `quota_exceeded` 的 `429`。
3. `persistent`：HTTP `401`、`402`、`403`、`404`、`405`、`407`、`410`、`415` 或 `451`。
4. `rate_limited`：`rate_limit_error`、`rate_limit_exceeded` 或 `too_many_requests`。
5. `persistent`：`account_deactivated`、`account_suspended`、`authentication_error`、`deployment_not_found`、`invalid_api_key`、`model_not_found`、`model_not_supported`、`no_available_account`、`permission_denied`、`quota_exceeded` 或 `unsupported_model`。
6. `transient`：HTTP `408`、HTTP `5xx`，或 `overloaded_error`、`server_error`、`service_unavailable`、`temporarily_unavailable`。超时和连接失败也属于暂时性故障。

启用熔断器后，转发失败的最终类别决定熔断行为：

| 最终类别 | 被动熔断 | 重试同一 Channel | 其他 Channel 的失败采样 |
| --- | --- | --- | --- |
| `persistent` | 立即熔断 | 不重试 | 不采样 |
| `rate_limited` | 累计至阈值；触发熔断后，由遵守限流设置决定等待时间 | 仅在内置重试规则允许时 | 不采样 |
| `transient` | 累计至阈值 | 仅在内置重试规则允许时 | 可能为同一 Provider 中符合条件的同源 Channel 记录一次失败 |

只有可重试的暂时性 HTTP `502`、`503` 或 `524` 错误响应才会影响其他 Channel，流中的错误不会。基址的协议、主机和端口相同即为同源。规则可以让 HTTP `400` 计入健康状态，但不能让它变得可重试。规则不能增加内置规则不允许的重试。

### 主节点上的探测恢复

主节点通过主动探测恢复非 Replicate Channel。通常，Monoize 在熔断后等待一个探测间隔，再发起首次探测。探测失败会将连续成功次数清零，再等一个间隔后发起下一次探测。下文的限流规则可替换这两种等待时间。

连续成功次数达到阈值后，Channel 或模型才会恢复健康。探测成功但未达到阈值时，Monoize 会在一个间隔后安排下次探测。探测间隔结束只意味着可以探测，不会恢复转发流量。Monoize 不探测已禁用的 Provider、已禁用的 Channel 或权重为零的 Channel。

| 探测设置 | 全局设置键 | Provider 或 Channel 覆盖字段 | 默认值 |
| --- | --- | --- | --- |
| 探测间隔 | `monoize_active_probe_interval_seconds` | `active_probe_interval_seconds_override` | 30 秒 |
| 成功阈值 | `monoize_active_probe_success_threshold` | `active_probe_success_threshold_override` | 成功 1 次 |
| 探测模型 | `monoize_active_probe_model` | `active_probe_model_override` | `null` |
| 流式探测 | `monoize_active_probe_stream` | `active_probe_stream_override` | 开启（`true`） |

每项设置都按 Channel 覆盖值、Provider 覆盖值、全局值的顺序采用第一个非 `null` 值。将流式探测的覆盖值设为 `false` 表示关闭，不会继续继承。

按 Channel 熔断时，如果配置的探测模型由该 Channel 提供，就使用该模型。如果没有配置，或该 Channel 不提供所配置的模型，则选择按字典序排列的第一个逻辑模型键。启用 `per_model_circuit_break` 后，Monoize 用各不健康模型自己的逻辑模型键进行探测。

Responses、Chat Completions、Messages 和 Gemini 的探测请求起初只包含一条 `hi` 消息，输出上限为 16 个 token，默认请求流式响应。Monoize 先应用 Provider 的请求变换，再应用全局请求变换。变换可以修改输出上限或流式选项。Monoize 使用与普通转发相同的编码器，始终通过 HTTP 发送探测请求。变换或编码出错时，探测失败，不会向上游发送请求。

探测成功要求 HTTP 状态码为 `2xx`。流式探测还要求转发所用的解码器读到终止事件，且没有输出错误事件。非流式探测则要求该解码器成功解析响应体。图像和决策类 Channel 使用原生非流式探测，不应用变换，也不读取流式探测设置。

### 定时恢复

任何节点上的 Replicate Channel，以及副本节点上的所有 Channel，都采用定时恢复，不进行主动探测。常规等待时间（`cooldown_seconds`）默认为 60 秒。通过全局设置 `monoize_passive_cooldown_seconds` 或 Channel 的 `passive_cooldown_seconds_override` 调整。等待结束后，Channel 或模型无需探测即可恢复健康。

### 遵循上游限流

`monoize_honor_rate_limit` 默认为 `false`。通过 Provider 或 Channel 的 `honor_rate_limit_override` 覆盖全局设置。Monoize 按 Channel、Provider、全局的顺序，使用第一个非 `null` 值。显式设为 `false` 表示关闭，而不是继承。

开启后，如果触发熔断的故障最终归类为 `rate_limited`，首次探测或定时恢复前会改用限流冷却时间。该时间默认为 15 秒。通过全局设置 `monoize_passive_rate_limit_cooldown_seconds` 或 Channel 的 `passive_rate_limit_cooldown_seconds_override` 调整。

如果上游返回了有效且更长的 `Retry-After`，Monoize 会采用该值。比较前，Monoize 会将从响应头解析出的时长限制在 3600 秒以内。有效的 `retry-after-ms` 优先于 `Retry-After`，并向上取整到秒。如果探测本身受到限流，则根据该次探测的响应应用同一规则。关闭此设置时，限流错误仍使用常规探测间隔或定时恢复等待时间。

### 仪表盘测试和启用开关

运行 [Channel 测试](/zh/docs/dashboard/providers-and-channels)，无需等待主动探测即可确认是否恢复。测试与主动探测使用相同的请求处理流程和成功判定规则。对补全类测试，**快速测试**使用 Channel 的生效流式设置；在测试对话框中可以选择初始流式模式。该测试不支持 Replicate 补全请求。

测试通过后，被测 Channel 或模型恢复健康。启用熔断器时，如果测试遇到持久性上游故障，被测对象会变为不健康。如果已经不健康，原来的恢复安排不变。其他测试失败不会改变健康状态。启用 `per_model_circuit_break` 时，测试只影响被测模型。

启用或禁用 Channel 都会清除其健康记录，包括各模型的健康状态。

## 会话亲和

Monoize 可以优先选择此前服务该会话的 Channel。可在全局或 Channel 层配置亲和。优先 Channel 仍须满足资格和健康规则。Responses 的 `previous_response_id` 历史由 Monoize 在内部解析，不要求上游保存状态。

## 时间指标

[请求日志](/zh/docs/request-logs)中的每一行记录总耗时、首字节时间和可见输出的每秒 Token 数。修改权重之前，用这些数值比较各个 Channel。
