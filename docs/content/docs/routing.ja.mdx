## ルート選択

有効なサブスクリプションがある場合、Monoize は Provider の選択前に、キーとサブスクリプションの両方に含まれるグループへ絞り込みます。
キーのグループ順序は維持されます。リクエストは、この共通グループに属する Provider のみを使用できます。

Monoize は各リクエストのルートを次の順序で解決します。

1. **モデルリダイレクト。** API キーのルールが先に実行され、次にグローバルルールが実行されます。最初に一致したルールがモデル名を書き換えます。
2. **Provider 選択。** Monoize は次の条件を満たす有効な Provider を収集します: 有効かつ重みが 0 より大きい Channel が対象モデルを 1 つ以上提供していること、およびグループがキーのグループと交差していること。グループの順序が優先順位を決めます。同一グループ内では Provider の優先度が適用されます。
3. **Channel 選択。** 選択された Provider 内で、Monoize は候補 Channel を重み付きランダムで並べます。Channel $i$ が最初に試行される確率は次のとおりです。

```math
P(i) = \frac{w_i}{\sum_{j=1}^{n} w_j}
```

したがって、重み `2` の Channel は重み `1` の Channel の 2 倍のトラフィックを受けます。

## リトライとフォールバック

Monoize はルートを入れ子順で試行します。まず 1 つの Provider 内の Channel を試し、次の Provider へ進みます。

- 各 Channel は `channel_max_retries + 1` 回の試行を得ます。デフォルトは 1 回で、Channel 内リトライはありません。
- `channel_retry_interval_ms` は Channel 内リトライの間に待機を挿入します。デフォルトは `0` です。
- `max_retries` は Provider 全体の合計試行回数を制限します。
- 1 つの Provider を使い切ると、Monoize は次の適格な Provider へ進みます。
- すべての Provider を使い切ると、クライアントは最後に失敗した試行のステータスとエラーを受け取ります。[エラーレスポンス](/ja/docs/endpoints)を参照してください。
- 最後の上流が `401`、`403`、`407` を返した場合は、コード `upstream_error` の `502` を返します。試行が 1 つもないリクエストも `502 upstream_error` を返します。

### 同一 Channel をリトライするエラー

| エラー | 同一 Channel リトライ | 次のルートへ前進 |
| --- | --- | --- |
| 恒久的な障害に該当しない HTTP `408`、`429`、`5xx` | あり | あり（Channel の試行回数を使い切った後） |
| タイムアウト、接続拒否・リセット | あり | あり（Channel の試行回数を使い切った後） |
| クレジット切れなどの恒久的な上流障害 | なし | あり（直ちに前進） |
| その他の上流エラー（例: `400`、`401`、`404`） | なし | あり（直ちに前進） |
| 上流プロトコルでリクエスト内のメディアを表現できない | なし | あり（直ちに前進） |
| その他の Monoize 側のエラー（例: 認証、残高、リクエストの検証やエンコード、課金） | なし | なし（ルーティング終了） |

## ストリーミング保証

Monoize は最初の上流試行が受理された後に SSE レスポンスヘッダーを送ります。HTTP の試行は `2xx` ステータスで受理されます。上流 WebSocket の試行は、Provider 制御イベント以外の最初のイベントで受理されます。それ以前の失敗は、SSE ではなくネイティブの JSON エラーを返します。

ヘッダー送信後も、最初のプロトコルデータまたはエラーイベントまではフォールバックを続けます。Monoize はレスポンス開始イベントと Provider 制御イベント（`codex.rate_limits` など）を最初の出力イベントまでバッファします。バッファの上限は 256 イベントです。SSE ハートビートはヘッダーの後に始まり、フォールバックを終了させません。

ヘッダー送信後にすべてのルートが失敗すると、HTTP ステータスはすでに `200` のため、エラーはストリーム内で届きます。最初のプロトコルイベント以降、Monoize は切り替えを行いません。したがって、可視ストリームは常に 1 回の生成に由来します。

## サーキットブレーカー

各 Provider には `circuit_breaker_enabled` があります。`false` にすると、Monoize はその Provider の健全性をルーティングの判定に使わなくなります。健全性の追跡とアクティブプローブも停止します。プローブ専用のスイッチはありません。

ダッシュボードには、Channel の状態が次の 3 種類で表示されます。

- **正常。** 他のルーティング条件も満たせば、Channel にトラフィックを転送できます。
- **異常。** 復帰するまで、Monoize はその Channel にリクエストを転送しません。
- **無効。** `enabled` が `false` です。サーキットブレーカーの設定に関係なく、その Channel にトラフィックは転送されません。

サーキットブレーカーが有効な場合、恒久的な障害が起きると Channel は直ちに異常になります。一時的な障害やレート制限エラーの場合、デフォルトでは 30 秒以内に 3 回失敗すると遮断します。`per_model_circuit_break` が有効な場合は、Channel 内のモデルごとに健全性を追跡します。あるモデルが異常でも、同じ Channel の他のモデルへの転送には影響しません。

上流が HTTP `429` を返しても、Monoize はクレジット切れを恒久的な障害として扱います。該当するエラーコードまたは種別は、`insufficient_quota`、`credit_balance_exhausted`、`credit_balance_too_low`、`insufficient_balance`、`billing_hard_limit_reached` です。恒久的な障害では、同じ Channel をリトライしません。`quota_exceeded` を含むその他の HTTP `429` エラーは、レート制限として扱います。

### プライマリノードでのプローブによる復帰

プライマリノードでは、Replicate 以外の Channel をアクティブプローブで復帰させます。後述のレート制限ルールが適用されない場合は、遮断からプローブ間隔の分だけ待って初回のプローブを実行します。プローブが失敗すると、連続成功回数を 0 に戻します。同じルールが適用されない限り、次のプローブまで再び同じ間隔を空けます。

連続成功回数がしきい値に達すると、Channel またはモデルが正常に戻ります。プローブが成功してもしきい値に達しなければ、同じ間隔を空けて次のプローブを実行します。プローブ間隔が過ぎればプローブを実行できますが、トラフィックの転送は再開しません。無効な Provider、無効な Channel、重みが 0 の Channel はプローブの対象外です。

| プローブ設定 | グローバル設定キー | Provider または Channel の上書き項目 | デフォルト |
| --- | --- | --- | --- |
| プローブ間隔 | `monoize_active_probe_interval_seconds` | `active_probe_interval_seconds_override` | 30 秒 |
| 成功しきい値 | `monoize_active_probe_success_threshold` | `active_probe_success_threshold_override` | 成功 1 回 |
| プローブモデル | `monoize_active_probe_model` | `active_probe_model_override` | `null` |
| ストリーミング | `monoize_active_probe_stream` | `active_probe_stream_override` | 有効（`true`） |

各設定は、Channel の上書き値、Provider の上書き値、グローバル設定の順に、最初の `null` でない値を使います。ストリーミングの上書き値を `false` にすると、次の設定を継承せずにストリーミングを無効にします。

Channel 単位で遮断する場合、設定したプローブモデルをその Channel が提供していれば、そのモデルを使います。未設定の場合や、その Channel が指定モデルを提供していない場合は、論理モデルのキーを辞書順に並べた先頭を使います。`per_model_circuit_break` が有効な場合は、異常になったモデルごとに、そのモデル自身の論理モデルキーでプローブを実行します。

Responses、Chat Completions、Messages、Gemini のプローブでは、`hi` というメッセージを 1 件用意し、出力上限を 16 トークンに設定します。デフォルトではストリーミング応答を要求します。Monoize は Provider のリクエスト変換を先に適用し、次にグローバルのリクエスト変換を適用します。変換によって出力上限やストリーミングの設定が変わることがあります。通常の転送と同じエンコーダーを使い、プローブは常に HTTP で送信します。変換やエンコードでエラーが起きた場合、上流にリクエストを送らずにプローブを失敗と判定します。

プローブの成功には HTTP `2xx` が必要です。ストリーミングでは、通常の転送と同じデコーダーがエラーイベントを出力せずに終端イベントまで到達する必要があります。非ストリーミングでは、同じデコーダーでレスポンス本文を正常に読み取れる必要があります。画像と意思決定用の Channel は、各 API 固有の非ストリーミングプローブを使います。これらには変換もストリーミング設定も適用されません。

### 待機時間による復帰

どのノードでも Replicate Channel は、アクティブプローブの代わりに待機時間による復帰を使います。レプリカノードでは、すべての Channel がこの方式を使います。通常の待機時間（`cooldown_seconds`）はデフォルトで 60 秒です。グローバルの `monoize_passive_cooldown_seconds` または Channel の `passive_cooldown_seconds_override` で変更できます。待機時間が過ぎると、プローブを実行せずに Channel またはモデルが正常に戻ります。

### 上流のレート制限に従う

`monoize_honor_rate_limit` のデフォルトは `false` です。Provider または Channel の `honor_rate_limit_override` で上書きできます。Monoize は Channel、Provider、グローバルの順に、最初の `null` でない値を使います。上書き項目を明示的に `false` にすると、設定を継承せずに無効にします。

有効にすると、レート制限で遮断した場合に、通常の待機時間の代わりにレート制限用のクールダウンを使います。この待機時間は、初回のプローブまたは待機時間による復帰までに適用されます。クレジット切れには、HTTP `429` が返ってもこのルールを適用しません。レート制限用のクールダウンはデフォルトで 15 秒です。グローバルの `monoize_passive_rate_limit_cooldown_seconds` または Channel の `passive_rate_limit_cooldown_seconds_override` で変更できます。

上流が有効な `Retry-After` を返し、その値がクールダウンより長い場合は、その値を使います。Monoize は比較前に、ヘッダーから読み取った待機時間を最大 3600 秒に制限します。有効な `retry-after-ms` は `Retry-After` より優先され、秒単位に切り上げます。プローブ自体がレート制限を受けた場合も、そのプローブのレスポンスに同じルールを適用します。この設定が無効な場合、レート制限エラーでも通常のプローブ間隔または復帰までの待機時間を使います。

### ダッシュボードでのテストと有効化スイッチ

アクティブプローブを待たずに復帰を確認するには、[Channel テスト](/ja/docs/dashboard/providers-and-channels)を実行してください。テストでは、アクティブプローブと同じリクエスト処理と成功判定を使います。補完リクエストをテストする場合、**クイックテスト**は Channel に適用されるストリーミング設定を使います。テストダイアログでは、変換前のストリーミング設定を選べます。このテストは Replicate の補完リクエストには対応していません。

テストが成功すると、対象の Channel またはモデルが正常に戻ります。サーキットブレーカーが有効で、テストが恒久的な上流障害で失敗した場合は異常になります。すでに異常であれば、復帰の予定は変わりません。その他のテスト失敗では、健全性は変わりません。`per_model_circuit_break` が有効な場合、テストの結果が影響するのは対象モデルだけです。

Channel を有効または無効に切り替えると、モデルごとの状態も含め、Channel の健全性の記録が消去されます。

## セッションアフィニティ

Monoize は、そのセッションを処理した Channel を優先できます。アフィニティはグローバルまたは Channel 単位で設定します。優先 Channel にも適格性と健全性のルールが適用されます。Responses の `previous_response_id` 履歴は Monoize 内で解決するため、上流による状態保持は不要です。

## タイミング指標

[リクエストログ](/ja/docs/request-logs)の各行には、合計時間、最初のバイトまでの時間、可視出力の秒間トークン数が記録されます。重みを変更する前に、これらの値で Channel を比較してください。
